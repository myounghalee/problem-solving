# [LeetCode 209] Minimum Size Subarray Sum — 늘리고, 조건을 만족하면 줄여보는 슬라이딩 윈도우

- 문제 번호: 209
- 링크: https://leetcode.com/problems/minimum-size-subarray-sum/
- 난이도: Medium
- 태그: Array, Binary Search, Sliding Window, Prefix Sum
- 사용 자료구조/알고리즘: **가변 크기 슬라이딩 윈도우**

## 1. 문제 요약

양의 정수 배열 `nums`에서, **합이 `target` 이상인 부분 배열(연속 구간) 중 가장 짧은 것**의 길이를 구한다. 없으면 `0`.

```text
예시) target=7, nums=[2,3,1,2,4,3] → 2   ([4,3]의 합이 7)
```

## 2. 접근 아이디어

### "모든 값이 양수"라는 제약이 슬라이딩 윈도우를 가능하게 한다

브루트포스(모든 구간 검사)는 `O(n²)`이라 `n≤10^5`에서 시간 초과다. 대신 이 문제의 제약 — **모든 원소가 양수** — 을 이용하면 윈도우를 `O(n)`에 움직일 수 있다.

값이 전부 양수이므로:

- 윈도우 **오른쪽**을 늘리면 합은 **항상 증가**한다.
- 윈도우 **왼쪽**을 줄이면 합은 **항상 감소**한다.

이 단조성 덕분에 "합이 부족하면 늘리고, 조건을 만족하면 줄여본다"는 전략이 안전하게 성립한다. [76번(Minimum Window Substring)](../76-minimum-window-substring/Solution.md)과 정확히 같은 뼈대다 — 다만 조건이 "문자 개수를 맞춘다"가 아니라 "합이 `target` 이상"일 뿐이다.

### 로직

- `right`를 오른쪽으로 한 칸씩 밀며 `sum`에 더한다.
- `sum >= target`이 되는 동안(`while`), **지금 윈도우 길이로 최솟값을 갱신**하고 `left`를 오른쪽으로 밀어 `sum`을 줄인다. 조건이 깨지면 멈춘다.
- 끝까지 한 번도 조건을 만족하지 못했으면 `0`을 반환한다.

### 손으로 시뮬레이션 — `target=7, nums=[2,3,1,2,4,3]`

| `right` | 더한 값 | `sum` | `while` 안에서 일어나는 일 | 그 시점의 최솟값 |
|---|---|---|---|---|
| 0 | `2` | 2 | 조건 미달, 그냥 넘어감 | ∞ |
| 1 | `3` | 5 | 조건 미달 | ∞ |
| 2 | `1` | 6 | 조건 미달 | ∞ |
| 3 | `2` | 8 | 윈도우 `[0,3]` 길이4 기록 → `nums[0]=2` 빼고 `sum=6, left=1` (다시 미달이라 종료) | 4 |
| 4 | `4` | 10 | 윈도우 `[1,4]` 길이4 기록 → `nums[1]=3` 빼고 `sum=7, left=2` → 아직 만족 → 윈도우 `[2,4]` 길이3 기록 → `nums[2]=1` 빼고 `sum=6, left=3` (미달, 종료) | 3 |
| 5 | `3` | 9 | 윈도우 `[3,5]` 길이3 기록(갱신 없음) → `nums[3]=2` 빼고 `sum=7, left=4` → 아직 만족 → 윈도우 `[4,5]`(`[4,3]`) 길이2 기록 → `nums[4]=4` 빼고 `sum=3, left=5` (미달, 종료) | **2** |

최종 답은 `2` — 윈도우 `[4,5]`, 즉 `[4,3]`(합 `7`)에서 나온다. `right=4`에서 조건을 두 번 연달아 만족해 `while`이 두 바퀴 도는 것처럼, 한 번의 `right` 전진이 여러 번의 축소로 이어질 수 있다는 점을 눈여겨보자.

## 3. 코드 (Java)

```java
class Solution {
    public int minSubArrayLen(int target, int[] nums) {

        int left = 0;
        int minLength = Integer.MAX_VALUE;
        int sum = 0;
        for (int right = 0; right < nums.length; right++) {
            sum += nums[right];
            while (sum >= target) {
                minLength = Math.min(minLength, right - left + 1);
                sum -= nums[left++];
            }
        }

        return minLength == Integer.MAX_VALUE ? 0 : minLength;
    }
}
```

### 코드 설명

- `minLength`를 **`while` 안에서** 갱신한다. 조건을 만족하는 순간마다 그때의 길이가 후보이기 때문이다. [76번](../76-minimum-window-substring/Solution.md)에서 이 위치를 놓쳐 정답을 잃어버린 적이 있었는데, 여기서는 처음부터 정확한 자리에 있다.
- `sum -= nums[left++]`로 왼쪽을 줄이며 다음 반복 조건(`sum >= target`)을 다시 검사한다. 조건이 계속 참인 동안 `while`이 여러 번 돌아 가능한 한 많이 줄인다 — 그래야 "지금 오른쪽 끝에서 만들 수 있는 가장 짧은 윈도우"를 놓치지 않는다.
- `minLength == Integer.MAX_VALUE`로 "한 번도 조건을 만족한 적 없음"을 판정한다. 값이 전부 양수라 실제 윈도우 길이가 `Integer.MAX_VALUE`가 될 수 없으므로 이 센티넬은 안전하다.

## 4. 복잡도 분석

- **시간복잡도**: `O(n)` — `right`는 `0`부터 `n-1`까지 한 번만 전진한다. `left`도 전체 실행을 통틀어 최대 `n`번만 전진하는 단조 증가 값이므로, `while`의 총 실행 횟수를 다 합쳐도 `O(n)`을 넘지 않는다.
- **공간복잡도**: `O(1)` — 변수 몇 개뿐.

실측: 제약 상한 `n=100,000`에서, 답이 없는 경우(0ms)와 매 단계 윈도우가 줄어드는 최악의 압축 빈도(`target=1`, 전부 `1`인 배열, 1ms) 모두 빠르다.

## 5. 엣지 케이스

- **원소 하나가 `target`과 같음** (`nums=[5], target=5`): 첫 반복에서 바로 조건을 만족해 길이 `1`.
- **답이 없음** (`target=11`, 배열 총합이 `8`): `while`이 한 번도 실행되지 않아 `minLength`가 초기값 그대로 남고 `0`을 반환한다.
- **배열 전체를 다 더해야 함** (`target=15`, `[1,2,3,4,5]`, 총합 `15`): `right`가 끝까지 가야 조건을 처음 만족한다.
- **큰 값 하나가 뒤쪽에 있음** (`[1,1,1,1,100,1,1]`, `target=100`): 앞의 작은 값들이 계속 쌓이다가, `100`을 만나는 순간 그 하나만으로 조건을 만족해 길이 `1`이 나온다. 슬라이딩 윈도우가 앞부분을 억지로 포함시키지 않고 정확히 좁혀진다는 걸 보여준다.

검증: 무작위 20,000건을 브루트포스와 교차 비교해 전부 일치했다.

## 6. Follow-up — `O(n log n)`: 누적합 + 이분 탐색

문제가 `O(n)`을 찾은 뒤 `O(n log n)`도 시도해보라고 명시적으로 요구한다. **누적합 배열이 단조 증가한다**는 점(이것도 "모든 값이 양수"라는 같은 제약에서 나온다)을 이용하면 이분 탐색이 가능해진다.

`prefix[i]`를 `nums[0..i-1]`의 합으로 정의하면(`prefix[0]=0`), 구간 `[i, j)`의 합은 `prefix[j] - prefix[i]`다. 각 시작점 `i`에 대해, `prefix[j] - prefix[i] >= target`을 만족하는 **가장 작은 `j`**를 찾으면 그게 `i`에서 시작하는 최단 윈도우다. `prefix`가 단조 증가하므로, 이 조건을 만족하는 `j`들은 항상 배열의 뒤쪽에 연속으로 몰려 있다 — 그래서 이분 탐색으로 그 경계를 찾을 수 있다.

```java
class Solution {
    public int minSubArrayLen(int target, int[] nums) {
        int n = nums.length;
        long[] prefix = new long[n + 1];
        for (int i = 0; i < n; i++) prefix[i + 1] = prefix[i] + nums[i];

        int best = Integer.MAX_VALUE;
        for (int i = 0; i <= n; i++) {
            long need = prefix[i] + target;
            int lo = i, hi = n;
            while (lo < hi) { // prefix[j] >= need 인 가장 작은 j (lower bound)
                int mid = (lo + hi) / 2;
                if (prefix[mid] >= need) hi = mid; else lo = mid + 1;
            }
            if (lo <= n && prefix[lo] >= need) best = Math.min(best, lo - i);
        }
        return best == Integer.MAX_VALUE ? 0 : best;
    }
}
```

`prefix`를 `long[]`으로 둔 이유는, `nums[i] ≤ 10^4`이고 `n ≤ 10^5`라 전체 합이 최대 `10^9`에 이를 수 있어 `int` 누적합이 위험할 수 있기 때문이다.

**비교** (`n=100,000` 기준):

| | 슬라이딩 윈도우 (3절) | 누적합 + 이분 탐색 (6절) |
|---|---|---|
| 시간복잡도 | `O(n)` | `O(n log n)` |
| 실측 | 1ms | 3ms |
| 핵심 아이디어 | 왼쪽·오른쪽 포인터가 각각 단조 이동 | 누적합의 단조성으로 이분 탐색 |

두 접근 모두 "모든 값이 양수"라는 같은 제약에서 단조성을 이끌어내지만, 그 단조성을 쓰는 방식이 다르다 — 슬라이딩 윈도우는 포인터를 직접 단조롭게 움직이고, 이분 탐색은 정렬(또는 정렬에 준하는 단조 배열)에서 흔히 쓰는 탐색 기법을 그대로 가져온다. 이 문제처럼 `O(n)`이 이미 가능한 경우 `O(n log n)`을 쓸 실익은 없지만, "슬라이딩 윈도우가 안 통하는 변형"(예: 음수가 섞여 누적합만 단조가 아니게 되는 경우, 정확히는 그때 이분 탐색도 함께 무너지지만)을 마주쳤을 때 누적합이라는 도구 자체를 꺼내보는 연습이 된다.
