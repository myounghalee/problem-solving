# [LeetCode 167] Two Sum II - Input Array Is Sorted — 투 포인터로 O(1) 공간에 풀기

- 문제 번호: 167
- 링크: https://leetcode.com/problems/two-sum-ii-input-array-is-sorted/
- 난이도: Medium
- 태그: Array, Two Pointers, Binary Search
- 사용 자료구조/알고리즘: **투 포인터(Two Pointers)**

## 1. 문제 요약

[1번(Two Sum)](../1-two-sum/Solution.md)과 같은 문제(합이 `target`이 되는 두 인덱스 찾기)이지만, 두 가지 조건이 추가된다.

- `numbers`가 **이미 오름차순 정렬**되어 있다.
- **추가 공간은 상수(`O(1)`)만** 써야 한다.
- 반환하는 인덱스는 **1부터 시작**한다(0-인덱스가 아님).

```text
예시) numbers = [2,7,11,15], target = 9 → [1,2]  (2+7=9, 1-인덱스)
      numbers = [2,3,4],      target = 6 → [1,3]  (2+4=6)
```

1번 문제의 해시맵 풀이는 `O(n)` 공간을 쓰므로 이번엔 못 쓴다. 대신 "정렬되어 있다"는 조건을 적극 활용해야 한다.

## 2. 접근 아이디어

정렬된 배열의 양 끝에서 시작하는 **투 포인터**를 쓴다.

- `l = 0`(가장 작은 값), `r = numbers.length - 1`(가장 큰 값)에서 시작한다.
- 두 값의 합을 `target`과 비교한다:
  - **합이 `target`보다 작다** → 더 큰 값이 필요하다는 뜻이므로 `l`을 오른쪽으로 한 칸 옮긴다(더 큰 값 쪽으로).
  - **합이 `target`보다 크다** → 더 작은 값이 필요하다는 뜻이므로 `r`을 왼쪽으로 한 칸 옮긴다(더 작은 값 쪽으로).
  - **합이 `target`과 같다** → 정답을 찾았다.
- `l`과 `r`이 서로 마주칠 때까지(`l < r`인 동안) 반복한다.

**왜 이게 항상 정답을 놓치지 않고 찾는가**: 배열이 정렬되어 있으므로, 합이 너무 작으면 두 값 중 "더 작은 쪽"(`l`)을 키워야만 합이 커질 수 있고, 합이 너무 크면 "더 큰 쪽"(`r`)을 줄여야만 합이 작아질 수 있다. 매 단계마다 `l`을 건드릴지 `r`을 건드릴지가 명확히 하나로 정해지기 때문에, 가능한 후보 쌍들을 하나도 건너뛰지 않고 `O(n)`에 전부 훑을 수 있다. 별도의 배열이나 맵 없이 인덱스 두 개만 유지하므로 공간은 `O(1)`이다.

### 손으로 시뮬레이션 — `numbers = [2, 7, 11, 15], target = 9`

| 단계 | `l` | `r` | `numbers[l] + numbers[r]` | 비교 | 동작 |
|---|---|---|---|---|---|
| 1 | 0 (`2`) | 3 (`15`) | 17 | `> 9` | `r--` |
| 2 | 0 (`2`) | 2 (`11`) | 13 | `> 9` | `r--` |
| 3 | 0 (`2`) | 1 (`7`) | 9 | `== 9` | 정답! |

`l=0, r=1`을 1-인덱스로 변환하면 `[1, 2]` — 정답과 일치한다.

## 3. 코드 (Java)

```java
class Solution {
    public int[] twoSum(int[] numbers, int target) {
        int l = 0, r = numbers.length - 1; // 양 끝에서 시작하는 두 포인터
        while (l < r) {
            if (numbers[l] + numbers[r] == target) return new int[]{l + 1, r + 1}; // 1-인덱스로 변환해서 반환
            if (numbers[l] + numbers[r] < target) l++; // 합이 작으면 더 큰 값 쪽으로
            else r--; // 합이 크면 더 작은 값 쪽으로
        }

        return new int[]{};
    }
}
```

### 코드 설명

- `l`, `r` 두 변수만으로 탐색 범위를 좁혀나간다 — 배열이나 해시맵 같은 추가 자료구조가 전혀 없으므로 공간복잡도가 `O(1)`이다.
- 문제가 요구하는 반환값은 1-인덱스이므로, 0-인덱스 기준으로 찾은 `l`, `r`에 각각 `+1`을 해서 반환한다.
- `l < r` 조건으로 루프를 도는 이유는 "같은 원소를 두 번 쓸 수 없다"는 제약 때문이다 — `l == r`이 되도록 허용하면 같은 인덱스를 두 번 쓰는 셈이 되므로, 두 포인터가 만나기 직전까지만 탐색한다.
- 정답이 항상 존재한다고 보장되므로, 마지막 `return new int[]{};`에는 실제로 도달하지 않는다.

## 4. 복잡도 분석

- **시간복잡도**: `O(n)` — `l`과 `r`이 서로를 향해 최대 `n`번 움직이며, 각 단계는 상수 시간.
- **공간복잡도**: `O(1)` — 포인터 변수 두 개 외에 추가 자료구조를 쓰지 않는다. 문제가 명시한 제약을 정확히 만족한다.

1번 문제의 해시맵 풀이(`O(n)` 시간, `O(n)` 공간)와 비교하면, 시간복잡도는 동일하지만 **공간복잡도를 `O(1)`로 줄인 것**이 이 문제의 핵심 개선점이다. 이게 가능했던 이유는 순전히 "배열이 정렬되어 있다"는 조건 덕분이다.

## 5. 엣지 케이스

- **음수를 포함하는 경우** (`[-1, 0], target = -1`): 정렬 순서와 투 포인터 비교 로직은 부호와 무관하게 그대로 동작한다.
- **중복된 값이 있는 경우** (`[0, 0, 3, 4], target = 0`): `l`과 `r`이 서로 다른 인덱스를 가리키는 한 같은 값이어도 문제없이 처리된다.
- **배열 길이가 최소(2)인 경우**: `l=0, r=1`에서 시작해 바로 비교하고 끝난다.
- **극값**(`numbers[i]`, `target`이 각각 `-1000`/`1000` 범위 양 끝): 정수 연산 범위 안이라 오버플로 걱정 없이 그대로 동작한다.

- [Two Sum (LeetCode 1)](../1-two-sum/Solution.md) — 정렬되지 않은 배열 버전. 해시맵으로 `O(n)` 시간/공간에 풀었다. 이 문제와 비교하면 "정렬 여부"가 접근 방식(해시맵 vs 투 포인터)을 완전히 바꾼다는 걸 잘 보여준다.
