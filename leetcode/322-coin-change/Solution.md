# [LeetCode 322] Coin Change — 메모이제이션 재귀로 "동전 종류 전체를 시도"하는 DP

- 문제 번호: 322
- 링크: https://leetcode.com/problems/coin-change/
- 난이도: Medium
- 태그: Array, Dynamic Programming, Breadth-First Search
- 사용 자료구조/알고리즘: **메모이제이션 재귀(Top-down DP)**

## 1. 문제 요약

동전 종류 `coins`(각 종류는 무한히 있음)와 목표 금액 `amount`가 주어질 때, `amount`를 만드는 데 필요한 **최소 동전 개수**를 구한다. 만들 수 없으면 `-1`.

```text
예시) coins=[1,2,5], amount=11 → 3   (5+5+1)
      coins=[2], amount=3 → -1       (홀수라 절대 못 만듦)
```

## 2. 접근 아이디어

### 그리디가 통하지 않는다

"가장 큰 동전부터 채운다"는 그리디 전략이 떠오르기 쉽지만, 이 문제에서는 반례가 존재한다.

```text
coins = [1, 3, 4], amount = 6
그리디(큰 것부터): 4 + 1 + 1 = 3개
최적:              3 + 3 = 2개
```

미국 동전 체계(1,5,10,25)에서는 그리디가 우연히 최적과 일치해서 착각하기 쉽지만, 일반적인 동전 조합에서는 성립하지 않는다. 그래서 **가능한 선택을 전부 시도해보고 그중 최선을 골라야** 한다 — DP가 필요한 이유다.

### "이 금액을 만드는 최소 개수"를 부분 문제로 정의한다

`amount`를 만들려면, **마지막에 어떤 동전을 썼는지**를 기준으로 나눠 생각할 수 있다. 마지막 동전이 `coin`이었다면, 그 전까지는 `amount - coin`을 최소 개수로 만들어 놨어야 한다.

```text
f(amount) = 1 + min( f(amount - coin) )  (coins의 모든 coin에 대해, amount >= coin인 것만)
```

즉 "amount원을 만드는 최소 개수"는 "동전 하나를 미리 써보고, 남은 금액을 최소 개수로 만드는 것"들 중 가장 좋은 선택에 `1`을 더한 것이다. 같은 부분 문제(`f(작은 금액)`)가 여러 경로에서 반복해서 필요해지므로, 한 번 계산한 값을 **메모이제이션**으로 저장해 재사용한다.

### 기저 조건

- `f(0) = 0` — 이미 목표를 달성했으니 동전이 더 필요 없다.
- 어떤 동전으로도 줄일 수 없는 금액(모든 `coin`이 남은 금액보다 큰데 `0`도 아닌 경우)은 `f(amount) = -1`(불가능)이다.

### 손으로 시뮬레이션 — `coins=[1,2,5], amount=11`

일부만 추려서 보면:

| 호출 | 시도하는 동전 | 재귀 결과 | 선택 |
|---|---|---|---|
| `f(11)` | 1→`f(10)`, 2→`f(9)`, 5→`f(6)` | `f(10)=2`(계산됨), `f(9)=2`, `f(6)=2` | `min=2` → `f(11)=3` |
| `f(6)` | 1→`f(5)`, 2→`f(4)`, 5→`f(1)` | `f(5)=1`, `f(4)=2`, `f(1)=1` | `min=1` → `f(6)=2` |
| `f(1)` | 1→`f(0)` | `f(0)=0` | `min=0` → `f(1)=1` |

`f(0)=0`이 모든 재귀의 바닥이고, 거기서부터 값이 쌓여 올라온다. 최종 `f(11)=3`.

## 3. 코드 (Java)

```java
class Solution {

    int[] dp; // dp[a] = 금액 a를 만드는 최소 동전 개수. 0이면 아직 계산 안 함(amount==0은 별도 처리)

    public int coinChange(int[] coins, int amount) {
        dp = new int[amount + 1];
        return dfs(coins, amount);
    }

    private int dfs(int[] coins, int amount) {
        if (amount == 0) return 0;
        if (amount < 0) return -1;
        if (dp[amount] != 0) return dp[amount]; // 이미 계산된 값(양수든 -1이든) 재사용

        int min = Integer.MAX_VALUE;
        for (int coin : coins) {
            if (amount >= coin) { // ==도 포함: 정확히 이 동전 하나로 끝나는 경우도 재귀가 처리
                int tmp = dfs(coins, amount - coin);
                if (tmp >= 0 && min > tmp) min = tmp; // -1(불가능)은 후보에서 제외
            }
        }
        dp[amount] = min == Integer.MAX_VALUE ? -1 : min + 1;
        return dp[amount];
    }
}
```

### 코드 설명

- **`dp[amount] != 0`으로 "이미 계산됨"을 판정한다.** 이게 성립하려면 계산된 값이 절대 `0`이 될 수 없어야 하는데, `amount >= 1`에 대해 최소 동전 개수는 항상 `1` 이상이거나 `-1`이므로 `0`은 나올 수 없다. `amount == 0`만 답이 `0`인데, 그건 함수 맨 위에서 재귀를 타지 않고 즉시 처리하므로 배열을 건드리지 않는다. 그래서 배열 기본값 `0`이 "아직 계산 안 함"을 뜻하는 것으로 충돌 없이 쓰인다.
- **`if (tmp >= 0 && min > tmp)`**: `tmp`가 `-1`(그 방향으로는 불가능)이면 후보에서 제외해야 한다. `>=` 인 이유는 `tmp`가 `0`일 수 있기 때문이다(`amount - coin == 0`, 즉 정확히 그 동전 하나로 끝나는 경우 `dfs`가 `0`을 반환한다). 이 `0`을 후보에서 빼면 "정확히 한 동전으로 딱 떨어지는" 최적해를 놓친다.
- **`dp[amount] = min == Integer.MAX_VALUE ? -1 : min + 1;`**: 어떤 동전을 써도 후보가 하나도 없었다면(전부 `-1`이었거나 애초에 `amount >= coin`인 동전이 없었다면) `min`이 초기값 그대로 남아 `-1`로 확정한다. 이 비교를 명시적으로 해야, `min`에 오버플로가 생기는 일 없이 "불가능"과 "0개로 가능"을 구분할 수 있다.
- `amount >= coin`(등호 포함)으로 정확히 딱 맞는 동전도 재귀에 자연스럽게 포함시킨다. 등호를 빼면 "이 동전 하나로 끝나는" 경우를 놓치므로, 그 경우만 별도로 처리하는 우회로가 필요해진다(6절 참고).

## 4. 복잡도 분석

- **시간복잡도**: `O(amount × coins.length)` — 메모이제이션 덕분에 서로 다른 `amount` 값 각각은 딱 한 번만 실제로 계산되고, 그 계산마다 동전 종류 수만큼 순회한다.
- **공간복잡도**: `O(amount)` — `dp` 배열과 재귀 호출 스택.

실측: 제약 상한(`coins.length=12`, `amount=10000`)에서 1ms.

## 5. 엣지 케이스

- **`amount == 0`**: 동전을 하나도 안 써도 되므로 `0`. 재귀 진입 전에 처리한다.
- **만들 수 없는 금액** (`coins=[2], amount=3`): 모든 경로가 `-1`로 막혀 최종적으로 `-1`.
- **동전 하나로 정확히 나누어떨어짐** (`coins=[1], amount=2`): `dfs(2) → dfs(1) → dfs(0)=0`으로 재귀가 자연스럽게 내려간다.
- **동전 값이 배열에 중복으로 들어간 경우** (`coins=[6,6], amount=6`): 같은 값이 여러 번 있어도 정답에는 영향이 없어야 한다(동전 `6`이 "무한히" 있다는 전제이므로, 배열에 몇 번 적혀 있는지는 무관하다). 이 케이스가 6절에서 다룰 함정의 근원이다.

검증: 무작위 30,000건(동전 값 범위를 좁혀 중복이 자주 나오게 함)을 표준 상향식 DP와 교차 비교해 전부 일치했다.

## 6. 겪었던 함정들

### (1) `-1`을 숫자처럼 `Math.min`에 넣어서 정답을 오염시킴

처음 버전은 `amount == coin`(등호)을 재귀에서 다루지 않고, 대신 생성자에서 `dp[coin]`을 미리 채워 우회했다. 그런데 이 우회로 대신 `Math.min`에서 `-1`을 걸러내지 않는 게 더 근본적인 문제였다.

```java
int tmp = dfs(coins, amount - coin);
min = Math.min(min, tmp);   // tmp가 -1(불가능)이어도 그냥 넣는다
```

`-1`은 "이 방향은 답이 아니다"라는 신호인데, 정수로 취급되어 어떤 양수 후보보다도 "작다"고 판정된다. 그 결과 **막다른 경로 하나가 정답 경로를 밀어낸다.**

```text
coinChange([2,3], 4) — 정답은 2(2+2)
dfs(4):
  coin=2 → dfs(2) = 1   (정답 경로, min=1)
  coin=3 → dfs(1) = -1  (동전이 없어 막다른 길)
           min = Math.min(1, -1) = -1   ← 정답 후보(1)가 밀려남
dp[4] = min+1 = 0 → "미계산"으로 오인되어 최종 -1 반환
```

고치는 법은 `tmp >= 0`(또는 `tmp != -1`)으로 불가능한 경로를 먼저 걸러내는 것이다(3절 코드).

### (2) `amount == 0`을 표현할 방법이 없어서 `0`이 `-1`이 되어버림

`-1`을 `Math.min`에 그냥 넣던 시절, `amount=0`에 대해서도 같은 문제가 생겼다. 시도할 동전이 없으니(`amount > coin`이 항상 거짓) `min`이 `Integer.MAX_VALUE`로 남고, `min + 1`이 오버플로되어 매우 큰 음수가 됐다. "0개면 충분하다"는 정답을 표현할 방법이 코드에 없었던 것이다.

```java
if (amount == 0) return 0;   // 재귀 맨 위에서 직접 처리
```

이 한 줄로 해결된다 — `amount=0`은 애초에 동전 선택 자체가 필요 없는 특수 케이스이므로, 일반적인 반복문 로직에 억지로 끼워 맞추지 않는 게 맞다.

### (3) 정답이 캐싱되지 않아 큰 입력에서 지수적으로 느려짐

(1)의 오염 때문에 `dp[amount]`가 `0`이나 음수로 잘못 계산되면, `dp[amount] > 0`으로 "계산됨"을 판정하던 초기 버전은 그 값을 캐시로 인정하지 않았다. 그래서 **같은 부분 문제를 방문할 때마다 매번 처음부터 다시 계산**했다.

```text
coins=[186,419,83,408]
  amount=1000  dfs 호출 689번
  amount=2000  dfs 호출 532,772번
  amount=3000  dfs 호출 396,882,557번 (1.3초)   ← 정답인데도 -1을 반환하며 이 지경까지 감
```

정상적인 메모이제이션이라면 `amount`가 늘 때 호출 수가 선형으로 늘어야 하는데, 폭발적으로 증가했다. `dp[amount] != 0`으로 판정 기준을 바꿔(양수든 음수든 `0`이 아니면 이미 계산됨) 이 문제가 해결됐다.

**교훈: 메모이제이션에서 "이미 계산됨"을 판정하는 조건은, 계산 가능한 모든 값(여기서는 양의 정수와 `-1`)을 빠짐없이 커버해야 한다.** `> 0`처럼 결과값의 일부만 커버하는 조건을 쓰면, 나머지 결과들은 캐시에 아예 들어가지 못한 것처럼 동작해 반복 계산으로 이어진다.

### (4) 동전 배열에 중복된 값이 있으면 사전 채움이 개수를 두 번 셈

`amount == coin`을 재귀 밖에서 우회하려고 썼던 코드가 있었다.

```java
for (int coin : coins) {
    if (coin <= amount) dp[coin]++;   // 값이 아니라 등장 횟수를 센다
}
```

`coins = [6, 6]`이면 `6`을 두 번 마주쳐 `dp[6]`이 `2`가 된다. 실제로는 동전 `6` 하나면 충분한데(각 동전은 "무한히 있다"는 전제라 배열에 몇 번 적혀 있는지는 무관해야 한다), 이 코드는 배열 안의 **등장 횟수**를 개수로 착각한다.

```text
coinChange([6,6], 6) = 2   기대 1
```

가장 근본적인 해결은 이 사전 채움 자체를 없애는 것이다. `amount >= coin`(등호 포함)으로 바꾸면 `dfs(amount - coin) = dfs(0) = 0`이 재귀 안에서 자연스럽게 처리되어, 우회로 자체가 필요 없어진다(3절의 최종 코드).

**교훈: "특정 경우를 미리 계산해서 우회하는" 코드는, 그 경우가 일반 로직으로도 자연스럽게 처리되도록 조건 하나를 고치는 것보다 대개 더 위험하다.** 우회로는 원래 로직이 암묵적으로 가정한 것(여기서는 "배열의 각 값은 서로 다르다")을 깨뜨리기 쉽고, 그 가정이 깨지는 입력은 일반적인 예제로는 잘 드러나지 않는다.

## 7. 이런 방법도 있다 — BFS로 "최단 경로" 찾기

이 문제의 태그에 `Breadth-First Search`가 붙어 있는 이유는, 다른 관점에서 보면 이 문제가 **최단 경로 문제**이기 때문이다. `amount`를 정점으로, "동전 하나를 빼는 것"을 간선으로 삼으면, `amount`에서 `0`까지 가는 **최소 간선 수**가 곧 답이다. 가중치가 모두 `1`인 그래프의 최단 경로이므로 BFS로 풀 수 있다.

```java
import java.util.*;

class Solution {
    public int coinChange(int[] coins, int amount) {
        if (amount == 0) return 0;
        boolean[] visited = new boolean[amount + 1];
        Queue<Integer> queue = new LinkedList<>();
        queue.add(amount);
        visited[amount] = true;

        int steps = 0;
        while (!queue.isEmpty()) {
            steps++;
            int size = queue.size();
            for (int i = 0; i < size; i++) {
                int cur = queue.poll();
                for (int coin : coins) {
                    int next = cur - coin;
                    if (next == 0) return steps;      // 도착
                    if (next > 0 && !visited[next]) {
                        visited[next] = true;
                        queue.add(next);
                    }
                }
            }
        }
        return -1; // 큐가 비도록 0에 도달 못함
    }
}
```

레벨(`steps`)이 하나씩 늘어날 때마다 "동전을 하나 더 쓴 상태"를 전부 모아 처리하므로, `0`에 처음 도달하는 레벨이 곧 최소 동전 개수다. BFS는 **가중치 없는 그래프에서 최단 경로를 보장**하기 때문에 정확하다.

**비교:**

| | 메모이제이션 재귀 (3절) | BFS |
|---|---|---|
| 관점 | "최소 개수"를 부분 문제로 분해 | "0까지의 최단 경로" |
| 자료구조 | 배열(`dp`) + 재귀 스택 | 큐 + 방문 배열 |
| 중복 방문 처리 | `dp[amount] != 0`으로 재계산 방지 | `visited[]`로 재방문 방지 |
| 동전 중복 값에 대한 안전성 | 값 자체로 계산하므로 원래도 안전(사전 채움만 없으면) | 안전(애초에 값 기반 그래프 탐색) |

두 방식 모두 `O(amount × coins.length)`로 점근적으로 같다. DP가 "부분 문제로 나눠 푼다"는 관점을 보여준다면, BFS는 같은 문제를 "그래프 탐색"이라는 낯선 각도에서 보여준다는 점에서 함께 봐둘 값어치가 있다.
