# [LeetCode 125] Valid Palindrome — 필터링 + 양 끝에서 좁혀오는 투 포인터

- 문제 번호: 125
- 링크: https://leetcode.com/problems/valid-palindrome/
- 난이도: Easy
- 태그: Two Pointers, String
- 사용 자료구조/알고리즘: **투 포인터(Two Pointers)**

## 1. 문제 요약

문자열에서 **알파벳/숫자만 남기고 대소문자 구분 없이** 봤을 때 팰린드롬인지 판정한다.

```text
예시) "A man, a plan, a canal: Panama" → true  (걸러내면 "amanaplanacanalpanama")
      "race a car" → false
      " " → true  (걸러내면 빈 문자열, 빈 문자열은 팰린드롬으로 취급)
```

## 2. 접근 아이디어

### 두 단계로 나눈다 — "정제"와 "판정"

1. **정제**: 알파벳/숫자가 아닌 문자는 버리고, 알파벳은 전부 소문자로 통일한다.
2. **판정**: 정제된 문자열이 팰린드롬인지 확인한다. 이건 **양 끝에서 동시에 안쪽으로 좁혀오며 비교**하면 된다 — 왼쪽 인덱스와 오른쪽 인덱스가 서로 마주칠 때까지 한 글자씩 비교하고, 한 번이라도 다르면 그 자리에서 `false`를 반환한다.

정제된 문자열을 새로 만들어 저장해두면, 판정 단계는 원본 배열의 인덱스를 신경 쓸 필요 없이 깔끔하게 투 포인터로 처리된다.

### 손으로 시뮬레이션 — `"A man, a plan, a canal: Panama"`

정제: `"amanaplanacanalpanama"` (길이 21)

| `left` | `right` | 비교 | 결과 |
|---|---|---|---|
| `a`(0) | `a`(20) | 같음 | 계속 |
| `m`(1) | `m`(19) | 같음 | 계속 |
| ... | ... | ... | 계속 |
| 가운데(`p`, 10번째) 도달 | | `left >= right`가 되어 종료 | `true` |

한 곳도 어긋나지 않고 중앙까지 도달하면 팰린드롬이다.

## 3. 코드 (Java)

```java
class Solution {
    public boolean isPalindrome(String s) {

        StringBuilder sb = new StringBuilder();
        for (char c : s.toCharArray()) {
            if (c >= 'a' && c <= 'z') sb.append(c);
            else if (c >= 'A' && c <= 'Z') sb.append((char) (c + ('a' - 'A'))); // 로케일과 무관하게 직접 소문자로
            else if (c >= '0' && c <= '9') sb.append(c);
        }

        int left = 0;
        int right = sb.length() - 1;
        while (left < right) {
            if (sb.charAt(left++) != sb.charAt(right--)) return false;
        }

        return true;
    }
}
```

### 코드 설명

- 필터링을 세 개의 `if`/`else if`로 나눠, 소문자·대문자·숫자를 각각 처리한다. 대문자는 `c + ('a' - 'A')`로 소문자로 바꾸는데, 이는 ASCII에서 대문자와 소문자가 정확히 일정한 간격(`32`)만큼 떨어져 있다는 사실을 이용한 것이다.
- 세 조건 중 어디에도 해당하지 않는 문자(공백, 문장부호 등)는 그냥 건너뛴다(`sb`에 추가되지 않는다).
- `left++`와 `right--`가 비교식 안에서 함께 일어난다. 비교가 끝나면 항상 양쪽이 한 칸씩 안으로 좁혀진 상태가 된다.

## 4. 복잡도 분석

- **시간복잡도**: `O(n)` — 정제 단계와 판정 단계 모두 문자열을 한 번씩만 훑는다.
- **공간복잡도**: `O(n)` — 정제된 문자열을 담는 `StringBuilder`.

실측: 제약 상한(`n=200,000`)의 완전한 팰린드롬에서 2ms.

## 5. 엣지 케이스

- **알파벳/숫자가 하나도 없는 문자열** (`" "`, `".,"`): 정제 후 빈 문자열이 되고, `left(0) < right(-1)`가 애초에 성립하지 않아 루프가 돌지 않고 `true`를 반환한다.
- **글자가 하나뿐** (`"0"`): 정제 후 길이 1, `left == right`라 루프가 돌지 않고 `true`.
- **대소문자만 다른 두 글자** (`"Aa"`): 정제하면 `"aa"`로 같아져 `true`.
- **숫자와 알파벳이 겹치는 모양이라도 다른 문자** (`"0P"`): 정제하면 `"0p"`, `'0' != 'p'`라 `false`.

검증: 무작위 200,000건을 `Character.isLetterOrDigit`/`Character.toLowerCase` 기반의 표준 라이브러리 브루트포스와 교차 비교해 전부 일치했다.

## 6. 겪었던 함정 — `String.toLowerCase()`의 로케일 민감성

처음 버전은 문자 하나하나를 직접 처리하는 대신, `s.toLowerCase()`로 문자열 전체를 한 번에 소문자로 바꾼 뒤 필터링했다.

```java
for (char c : s.toLowerCase().toCharArray()) {
    if (((c - 'a') >= 0 && (c - 'a') < 26) || ...) sb.append(c);
}
```

이 코드는 준비된 예제와 무작위 10만 건 모두 통과했다. 하지만 `String.toLowerCase()`는 **JVM의 기본 로케일을 따라간다**는 잘 알려진 함정이 있다. 터키어 로케일(`tr-TR`)에서는 대문자 `I`를 소문자로 바꾸면 일반적인 `i`(코드 105)가 아니라 **점 없는 `ı`**(dotless i, 코드 305)가 된다.

```text
"I".toLowerCase()  (터키어 로케일)  →  "ı"  (코드 305)
```

이 `ı`는 `'a'~'z'`(97~122) 범위 밖이므로, 필터 조건 `(c - 'a') >= 0 && (c - 'a') < 26`을 통과하지 못해 **알파벳이 아닌 것처럼 조용히 걸러진다.** 그 결과:

```text
터키어 로케일에서 isPalindrome("Ix")
  "Ix".toLowerCase() = "ıx"
  필터링: 'ı'는 걸러짐, 'x'만 남음 → "x" (한 글자)
  한 글자는 항상 팰린드롬 → true 반환

실제로는 "ix"(i ≠ x)로 false여야 한다.
```

터키어 로케일에서 검증해서 이 반례를 재현했다. 로컬 개발 환경(미국/한국 로케일)에서는 `'I'.toLowerCase()`가 정상적으로 `'i'`가 되므로 **이 버그는 절대 재현되지 않는다** — 준비된 테스트도, 10만 건 무작위 퍼징도 전부 통과했던 이유다.

이 문제 자체가 실제로 틀릴 위험은 낮다(LeetCode 채점 서버가 터키어 로케일로 도는 경우는 없다). 하지만 **JVM 기본 로케일에 의존하는 문자열 처리는 실무에서 실제로 사고가 난 전례가 있는 패턴**이다(예: 서버 배포 환경의 로케일 설정에 따라 같은 코드가 다른 결과를 내는 경우). `String.toUpperCase()`/`toLowerCase()`의 Javadoc도 "로케일에 민감한 대소문자 변환이 필요 없다면 `Locale.ROOT`를 명시하라"고 경고한다.

**고치는 법**: 문자 하나하나를 직접 범위로 판정하고 변환하면 로케일이 개입할 여지 자체가 없어진다.

```java
if (c >= 'A' && c <= 'Z') c += ('a' - 'A');   // ASCII 범위 안에서 직접 계산
```

또는 `s.toLowerCase(Locale.ROOT)`처럼 로케일을 명시적으로 고정하는 방법도 있다. 이 문제는 입력이 ASCII로 한정되므로(`s`는 출력 가능한 ASCII 문자로만 구성) 전자가 더 직접적이다.

**교훈: `toLowerCase()`/`toUpperCase()`를 문자열 전체에 대고 호출할 때는, 그게 로케일에 의존하는 연산이라는 걸 의식하자.** 이 문제처럼 입력이 ASCII로 한정된 경우, 문자 하나씩 범위로 비교·변환하면 이런 종류의 환경 의존 버그가 원천적으로 생기지 않는다.
