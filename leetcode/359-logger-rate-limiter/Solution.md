# [LeetCode 359] Logger Rate Limiter — 해시맵으로 메시지별 "다음 허용 시각"만 기억하기

- 문제 번호: 359
- 링크: https://leetcode.com/problems/logger-rate-limiter/
- 난이도: Easy
- 태그: Hash Table, Design, Data Stream
- 사용 자료구조/알고리즘: **해시맵(`HashMap<String, Integer>`)으로 메시지별 최근 출력 시각 추적**

## 1. 문제 요약

타임스탬프와 함께 메시지 스트림을 받는 로거를 설계한다. 어떤 메시지는 **같은 메시지가 최근 10초 이내에 이미 출력된 적이 없을 때만** 출력되어야 한다. `shouldPrintMessage(timestamp, message)`가 호출될 때마다 출력 여부(`boolean`)를 반환한다.

## 2. 접근 아이디어

이 문제는 전형적인 **"이벤트마다 상태를 남기고, 다음 이벤트에서 그 상태를 조회해 판정하는"** rate limiter 패턴이다. 메시지가 워낙 다양할 수 있으므로, "최근 10초간 출력된 메시지 목록"을 통째로 들고 있을 필요 없이, **메시지별로 마지막 출력 시각 하나만** 기억하면 충분하다.

- `HashMap<String, Integer> map`에 `message → 마지막으로 출력을 허용한 timestamp`를 저장한다.
- `shouldPrintMessage(timestamp, message)`가 호출되면:
  1. 처음 보는 메시지면 무조건 출력을 허용하고, 이번 `timestamp`를 기록한다.
  2. 이미 기록이 있는 메시지면, `저장된 시각 + 10`과 지금 `timestamp`를 비교한다. `timestamp`가 아직 그 값에 못 미쳤으면(`저장된시각 + 10 > timestamp`) 차단, 그렇지 않으면(같거나 지났으면) 허용하고 `timestamp`로 갱신한다.

문제 제약이 "모든 타임스탬프는 비내림차순으로 들어온다"이므로, 굳이 과거 기록을 지우거나 정리할 필요가 없다 — 메시지당 최신 값 하나만 덮어쓰면 항상 정확하다.

### 손으로 시뮬레이션 — 예시 입력

| 호출 | timestamp | message | map 상태(호출 전) | 판정 | map 상태(호출 후) |
|---|---|---|---|---|---|
| 1 | 1 | "foo" | `{}` | 처음 봄 → **true** | `{foo: 1}` |
| 2 | 2 | "bar" | `{foo: 1}` | 처음 봄 → **true** | `{foo: 1, bar: 2}` |
| 3 | 3 | "foo" | `{foo: 1, bar: 2}` | `1 + 10 = 11 > 3` → **false** | 변화 없음 |
| 4 | 8 | "bar" | `{foo: 1, bar: 2}` | `2 + 10 = 12 > 8` → **false** | 변화 없음 |
| 5 | 10 | "foo" | `{foo: 1, bar: 2}` | `1 + 10 = 11 > 10` → **false** | 변화 없음 |
| 6 | 11 | "foo" | `{foo: 1, bar: 2}` | `1 + 10 = 11 > 11`은 거짓 → **true** | `{foo: 11, bar: 2}` |

6번째 호출이 이 문제의 핵심 경계값이다. `timestamp`가 "마지막 출력 + 10"과 **정확히 같을 때도 허용**해야 하므로, 비교를 `>` (엄격한 초과일 때만 차단)로 써야 한다. `>=`로 쓰면 `t=11`에서도 차단되어 틀린 답이 나온다.

## 3. 코드 (Java)

```java
import java.util.HashMap;
import java.util.Map;

class Logger {

    Map<String, Integer> map = new HashMap<>(); // message -> 마지막으로 출력을 허용한 timestamp

    public Logger() {}

    public boolean shouldPrintMessage(int timestamp, String message) {

        if (!map.containsKey(message)) {
            map.put(message, timestamp); // 처음 보는 메시지는 무조건 출력
            return true;
        }

        if (map.get(message) + 10 > timestamp) { // 아직 10초가 안 지났으면 차단
            return false;
        }

        map.put(message, timestamp); // 10초가 지났으면 허용하고 시각 갱신
        return true;
    }
}
```

### 코드 설명

- `map`은 메시지 전체 이력이 아니라 **가장 최근 출력 시각 단 하나**만 들고 있는다. 어차피 다음 판정에 필요한 건 "마지막으로 언제 출력했는가" 뿐이므로, 그 이전 기록은 의미가 없다.
- `map.get(message) + 10 > timestamp`가 참이면 아직 10초 창(window) 안이라 차단, 거짓이면 창을 벗어났으므로 허용한다. `timestamp == 저장된시각 + 10`인 경계에서 `>`가 거짓이 되어 정확히 허용되는 것이 문제의 예시(6번째 호출)와 일치한다.
- 두 분기(`!containsKey`, 시간 통과) 모두 결국 `map.put(message, timestamp)`로 갱신하고 `true`를 반환하는 동일한 동작이라, 코드를 더 줄일 수도 있지만(아래 "더 간결한 버전" 참고) 지금 형태가 판정 로직을 단계별로 읽기엔 더 명확하다.

## 4. 복잡도 분석

- **시간복잡도**: `O(1)` (호출당, 상각) — 해시맵 조회/삽입 한 번씩.
- **공간복잡도**: `O(M)` — `M`은 지금까지 등장한 **고유 메시지의 개수**. 제약상 호출이 최대 `10^4`번이므로 최악의 경우도 `O(10^4)`.

## 5. 엣지 케이스

- **경계값(`timestamp == 저장된 시각 + 10`)**: 반드시 허용해야 한다 — 비교 연산자를 `>=`가 아닌 `>`로 써야 한다 (3절 시뮬레이션의 6번째 호출).
- **처음 보는 메시지**: 무조건 허용. `map`에 아직 키가 없는 상태이므로 별도 분기로 처리한다.
- **타임스탬프가 비내림차순이라는 제약**: 이 덕분에 메시지별로 "지나간 출력 기록을 정리"할 필요가 없다 — 항상 최신 값 하나만 있으면 이후 판정이 정확하다. (만약 타임스탬프가 뒤섞여 들어올 수 있다면 슬라이딩 윈도우 로그처럼 더 복잡한 구조가 필요하다.)

## 6. 관련 문제

이벤트 스트림을 받으면서 **키(또는 메시지)별로 최소한의 상태만 해시맵에 남겨 다음 판정에 쓰는** 설계 계열.

- [LRU Cache (LeetCode 146)](../146-lru-cache/Solution.md) — 해시맵으로 키별 상태(값·최근 사용 여부)를 관리하며 매 호출마다 갱신한다는 점은 같지만, 이 문제는 시간(10초 창) 기준으로 통과/차단만 판정하면 되는 더 단순한 형태다.
- [Design Hit Counter (LeetCode 362)](../362-design-hit-counter/Solution.md) — 둘 다 "타임스탬프 스트림을 받아 시간 기준으로 판정한다"는 목적은 같지만, 이 문제는 메시지별 **마지막 시각 하나**만 해시맵에 남기면 충분한 반면, 362는 창 안의 **개수 전체**를 세야 해서 큐에 원본 타임스탬프를 계속 들고 있어야 한다는 점이 다르다.
