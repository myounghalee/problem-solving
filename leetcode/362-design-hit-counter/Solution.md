# [LeetCode 362] Design Hit Counter — 큐로 만드는 슬라이딩 윈도우 히트 카운터

- 문제 번호: 362
- 링크: https://leetcode.com/problems/design-hit-counter/
- 난이도: Medium
- 태그: Design, Queue, Binary Search, Data Stream
- 사용 자료구조/알고리즘: **`Deque`로 만드는 슬라이딩 윈도우(sliding window queue)**

## 1. 문제 요약

`hit(timestamp)`로 히트를 기록하고, `getHits(timestamp)`는 그 시점 기준 **지난 300초** (`[timestamp - 299, timestamp]` 구간) 동안 발생한 히트 수를 반환하는 `HitCounter`를 설계한다. 모든 호출은 타임스탬프가 단조 증가하는(시간순) 순서로 들어온다.

## 2. 접근 아이디어

"최근 N초 동안의 이벤트 수"를 구하는 문제는 전형적인 **슬라이딩 윈도우** 패턴이다. 타임스탬프가 항상 시간순으로 들어온다는 제약 덕분에, 히트를 큐(`Deque`)에 순서대로 쌓아두고 필요할 때 **창을 벗어난 오래된 항목만 앞에서부터 잘라내면** 된다.

- `hit(timestamp)`: 큐 뒤에 `timestamp`를 추가한다. (같은 타임스탬프가 여러 번 들어와도 그대로 각각 push — "히트 여러 개"를 표현)
- `getHits(timestamp)`:
  1. 큐 맨 앞(가장 오래된 히트)을 보면서, `timestamp - 300` 이하인(=창보다 오래된) 항목을 계속 제거한다.
  2. 정리가 끝난 뒤 큐에 남은 항목 수가 곧 지난 300초간의 히트 수다.

한 번 뒤에서 지워진 오래된 히트는 이후 다시 필요해질 일이 없다(타임스탬프가 항상 증가하므로) — 그래서 큐 앞에서만 잘라내는 것으로 충분하고, 별도의 순회나 재탐색이 필요 없다.

### 손으로 시뮬레이션 — 예시 입력

| 호출 | 큐 상태(호출 전) | 동작 | 큐 상태(호출 후) | 반환값 |
|---|---|---|---|---|
| `hit(1)` | `[]` | push 1 | `[1]` | - |
| `hit(2)` | `[1]` | push 2 | `[1, 2]` | - |
| `hit(3)` | `[1, 2]` | push 3 | `[1, 2, 3]` | - |
| `getHits(4)` | `[1, 2, 3]` | `peek(1) <= 4-300=-296`? 아니오 → 제거 없음 | `[1, 2, 3]` | **3** |
| `hit(300)` | `[1, 2, 3]` | push 300 | `[1, 2, 3, 300]` | - |
| `getHits(300)` | `[1, 2, 3, 300]` | `peek(1) <= 300-300=0`? 아니오 → 제거 없음 | `[1, 2, 3, 300]` | **4** |
| `getHits(301)` | `[1, 2, 3, 300]` | `peek(1) <= 301-300=1`? 예 → 1 제거. `peek(2) <= 1`? 아니오 → 중단 | `[2, 3, 300]` | **3** |

마지막 `getHits(301)` 호출에서 경계값이 드러난다. 타임스탬프 `1`은 창(`[301-299, 301] = [2, 301]`)에서 벗어나므로 제거되고, `2`부터는 창 안이라 남는다.

## 3. 코드 (Java)

```java
import java.util.ArrayDeque;
import java.util.Deque;

class HitCounter {

    Deque<Integer> q; // 히트 타임스탬프를 시간순(오름차순)으로 보관

    public HitCounter() {
        q = new ArrayDeque<>();
    }

    public void hit(int timestamp) {
        q.add(timestamp); // 큐 뒤에 새 히트 추가
    }

    public int getHits(int timestamp) {
        while (q.peek() != null && q.peek() <= timestamp - 300) {
            q.poll(); // 300초보다 오래된 히트를 앞에서부터 제거
        }
        return q.size(); // 남은 개수 = 지난 300초간 히트 수
    }
}
```

### 코드 설명

- `q`에는 히트 타임스탬프가 push된 순서(=시간순) 그대로 쌓인다. 큐 맨 앞이 항상 "가장 오래된 히트"이므로, 창을 벗어난 항목을 지우는 작업은 앞에서부터만 확인하면 된다.
- `q.peek() <= timestamp - 300`은 "`timestamp - peek >= 300`" 즉 300초 이상 지난 히트라는 뜻이다. 창이 `[timestamp - 299, timestamp]`이므로, `peek == timestamp - 299`인 경우는 창에 포함되어 제거되지 않아야 하는데, `timestamp - 299 <= timestamp - 300`은 거짓이라 실제로 제거되지 않는다 — 경계가 정확하다.
- `getHits`를 여러 번 호출해도, 이미 지워진 오래된 항목은 다시 큐에 나타나지 않으므로 각 항목은 평생 최대 한 번만 poll된다. 이 덕분에 `while` 루프가 있어도 전체 호출에 대한 **상각(amortized) 시간복잡도**는 `O(1)`이다.

## 4. 복잡도 분석

- **시간복잡도**: `hit`은 `O(1)`. `getHits`는 최악의 경우 창 밖 항목을 여러 개 지우지만, 항목 하나당 평생 한 번만 poll되므로 전체 호출에 대해 **상각 `O(1)`**이다.
- **공간복잡도**: `O(W)` — `W`는 현재 300초 창 안에 있는 히트 수. 문제 제약(`hit`+`getHits` 합쳐 최대 300번 호출)에서는 최악의 경우도 상수에 가깝다.

### 참고: Binary Search로도 풀 수 있다

큐 대신 모든 타임스탬프를 `List`(또는 배열)에 순서대로 저장해두고, `getHits`에서 `timestamp - 299` 이상인 첫 위치를 이분 탐색(`lower_bound`)으로 찾아 `size - 위치`를 반환하는 방식도 가능하다. 다만 이 경우 지워지지 않는 과거 기록이 계속 쌓여 공간이 `O(전체 hit 수)`로 늘어나므로, 창을 벗어난 데이터를 실제로 제거하는 큐 방식이 이 문제에는 더 적합하다.

## 5. 엣지 케이스

- **경계값(`timestamp - peek == 300`)**: 창(`[timestamp-299, timestamp]`) 밖이므로 제거되어야 한다 — `<=`로 비교해야 정확하다 (3절 시뮬레이션의 마지막 호출).
- **같은 타임스탬프에 여러 번 `hit`**: "같은 timestamp에 여러 번 히트가 발생할 수 있다"는 조건대로, `hit`을 호출한 횟수만큼 큐에 그대로 쌓이므로 자연스럽게 처리된다.
- **`hit` 없이 바로 `getHits` 호출**: 큐가 비어 있으면 `while` 조건의 `q.peek() != null`에서 바로 종료되고 `0`을 반환한다.
