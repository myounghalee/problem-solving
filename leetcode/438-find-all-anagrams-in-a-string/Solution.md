# [LeetCode 438] Find All Anagrams in a String — 슬라이딩 윈도우 + 문자 빈도 배열로 풀기

- 문제 번호: 438
- 링크: https://leetcode.com/problems/find-all-anagrams-in-a-string/
- 난이도: Medium
- 태그: Hash Table, String, Sliding Window
- 사용 자료구조/알고리즘: **고정 길이 슬라이딩 윈도우 + 문자 빈도 배열(`int[26]`)**

## 1. 문제 요약

문자열 `s`와 `p`가 주어질 때, `s`의 부분 문자열 중 `p`의 애너그램(같은 문자를 같은 개수만큼 포함하지만 순서만 다른 문자열)이 되는 모든 시작 인덱스를 찾는다.

```text
예시) s = "cbaebabacd", p = "abc" → [0, 6]
      s = "abab",      p = "ab"  → [0, 1, 2]
```

## 2. 접근 아이디어

애너그램인지 판단할 때 흔히 떠올리는 방법은 "두 문자열을 정렬해서 비교"하는 것이지만, 매 윈도우마다 정렬을 다시 하면 느리다. 대신 **애너그램은 "각 문자가 몇 개씩 있는지"만 같으면 된다**는 점에 주목하면, 정렬 없이도 `O(1)`에 윈도우를 갱신하며 비교할 수 있다.

- `s`와 `p`는 소문자 알파벳만 쓰므로, 문자별 개수를 `int[26]` 배열로 관리한다(`c - 'a'`로 인덱스를 구함). 개수를 셀 때 `boolean[26]`(존재 여부만)이 아니라 `int[26]`(정확한 개수)이 필요한 이유는, 애너그램은 문자 종류뿐 아니라 **각 문자의 개수까지** 같아야 하기 때문이다 (`"aab"`와 `"abb"`는 문자 종류는 같아도 애너그램이 아니다).
- `need`: `p`의 문자별 개수. 한 번만 계산해두고 끝까지 기준으로 재사용한다.
- `window`: 지금 보고 있는 `s`의 길이 `m`(`= p.length()`)짜리 구간의 문자별 개수.
- 처음엔 `window`를 `s`의 앞부분 `m`글자로 채우고 `need`와 비교한다.
- 그다음부터는 윈도우를 한 칸씩 오른쪽으로 옮기면서, **새로 들어오는 문자 하나는 `+1`, 왼쪽으로 빠지는 문자 하나는 `-1`**만 해주면 된다. 정렬처럼 전체를 다시 계산할 필요가 없다.
  - 이 두 연산(`+1`, `-1`)의 실행 순서는 결과에 영향을 주지 않는다. 서로 다른 문자라면 배열의 다른 칸을 건드리니 순서 무관하고, 같은 문자라면 `+1 -1`이든 `-1 +1`이든 최종 값은 항상 같다. 두 연산 사이에는 아무것도 확인하지 않고, 둘 다 끝난 뒤에만 `Arrays.equals`로 비교하기 때문이다.
- 매 윈도우마다 `window`와 `need`가 완전히 같으면(`Arrays.equals`), 그 윈도우의 시작 인덱스를 결과에 추가한다.

### 손으로 시뮬레이션 — `s = "abab", p = "ab"`

`need` = `{a:1, b:1}` (26칸짜리 배열이지만 여기선 값이 있는 문자만 표시)

| 단계 | 윈도우 | `window` | `need`와 같은가? |
|---|---|---|---|
| 초기 (`i=0..1`) | `"ab"` | `{a:1, b:1}` | 같음 → 인덱스 0 추가 |
| `i=2` 진입 (`'a'` 들어옴, `s[0]='a'` 나감) | `"ba"` | `{a:1, b:1}` | 같음 → 인덱스 1 추가 |
| `i=3` 진입 (`'b'` 들어옴, `s[1]='b'` 나감) | `"ab"` | `{a:1, b:1}` | 같음 → 인덱스 2 추가 |

결과: `[0, 1, 2]` — 정답과 일치한다.

## 3. 코드 (Java)

```java
import java.util.*;

class Solution {
    public List<Integer> findAnagrams(String s, String p) {
        List<Integer> result = new ArrayList<>();
        int n = s.length(), m = p.length();
        if (m > n) return result; // p가 s보다 길면 애초에 답이 없음

        int[] need = new int[26]; // p의 문자별 개수
        for (char c : p.toCharArray()) need[c - 'a']++;

        int[] window = new int[26]; // 현재 윈도우의 문자별 개수
        for (int i = 0; i < m; i++) window[s.charAt(i) - 'a']++;
        if (Arrays.equals(window, need)) result.add(0);

        for (int i = m; i < n; i++) {
            window[s.charAt(i) - 'a']++;       // 새로 들어오는 문자
            window[s.charAt(i - m) - 'a']--;   // 빠져나가는 문자
            if (Arrays.equals(window, need)) result.add(i - m + 1);
        }
        return result;
    }
}
```

### 코드 설명

- `need`는 `p`를 한 번만 훑어서 만든, 끝까지 변하지 않는 "정답 기준"이다.
- `window`는 처음엔 `s`의 앞부분 `m`글자로 초기화하고, 이후 반복마다 딱 두 칸(`+1`, `-1`)만 갱신한다 — 매번 새 배열을 만들거나 정렬하지 않는다.
- `i`는 "새로 들어오는 문자의 인덱스"를 가리키고, `i - m`은 "이번에 빠져나가는 문자의 인덱스"를 가리킨다. 윈도우 크기가 항상 `m`으로 고정되어 있기 때문에 이 대응이 성립한다.
- `if (m > n) return result;`로, `p`가 `s`보다 긴 경우를 맨 앞에서 걸러낸다. 이 체크가 없으면 `s.charAt(i)`에서 `i`가 `s`의 길이를 넘어가 예외가 날 수 있다.

## 4. 복잡도 분석

- **시간복잡도**: `O(n)` — `s`를 한 번만 훑으며, 각 위치에서 배열 갱신은 상수 시간(2칸), `Arrays.equals`도 배열 크기가 26으로 고정이라 사실상 상수 시간이다.
- **공간복잡도**: `O(1)` — `need`, `window` 모두 크기 26으로 고정, 입력 크기와 무관하다(결과 리스트 제외).

## 5. 엣지 케이스

- **`p`가 `s`보다 긴 경우** (`s="a", p="ab"`): `m > n`에서 바로 빈 리스트를 반환한다.
- **`s`와 `p`의 길이가 같은 경우** (`s="a", p="a"`): 초기 윈도우 하나만 검사되고 끝난다.
- **애너그램이 인접해서 겹치는 경우** (`"abab", "ab"`): 매 윈도우가 독립적으로 `need`와 비교되므로 겹침 여부와 무관하게 정확히 처리된다.
- **문자 종류는 같지만 개수가 다른 경우** (`"aab"` vs `"abb"`): `int[26]`으로 정확한 개수를 비교하므로 정확히 구분된다.

## 6. 이런 방법도 있다 — 윈도우를 정렬해서 비교 (더 느림)

가장 직관적으로 떠올리기 쉬운 방법은 "두 문자열을 정렬했을 때 완전히 같으면 애너그램"이라는 성질을 그대로 쓰는 것이다. `p`와 길이가 같은 `s`의 부분 문자열을 하나씩 잘라내(`System.arraycopy`), 그 조각을 정렬한 뒤 미리 정렬해둔 `p`와 비교한다.

```java
import java.util.*;

class Solution {
    public List<Integer> findAnagrams(String s, String p) {
        char[] cs = s.toCharArray();
        char[] cp = p.toCharArray();
        Arrays.sort(cp); // p는 한 번만 정렬해두고 기준으로 재사용

        List<Integer> list = new ArrayList<>();
        for (int i = 0; i <= cs.length - cp.length; i++) {
            char[] temp = new char[cp.length]; // 현재 윈도우 복사본

            System.arraycopy(cs, i, temp, 0, cp.length);
            Arrays.sort(temp);
            if (Arrays.equals(temp, cp)) list.add(i);
        }

        return list;
    }
}
```

이 방식의 근본적인 비효율은 **매번 윈도우를 처음부터 다시 정렬**한다는 점이다. 윈도우가 한 칸 옮겨갈 때 실제로 바뀌는 건 "빠지는 문자 하나"와 "들어오는 문자 하나"뿐인데, 정렬은 그 사실을 전혀 활용하지 못하고 매번 전체를 다시 계산한다.

**비교하면:**

| | 슬라이딩 윈도우 + 빈도 배열 (위 3.의 코드) | 윈도우를 정렬해서 비교 |
|---|---|---|
| 윈도우 갱신 비용 | `O(1)`(문자 2개만 갱신) | 매번 `O(m log m)`(전체 재정렬) |
| 시간복잡도 | `O(n)` | `O((n-m+1) · m log m)` |
| 같은 입력(`n=30000, m=10000`) 실측 | 약 1ms | 약 850ms |

`n`과 `m`이 둘 다 클 때는 정렬 기반 방식이 확연히 느려진다. 이 문제의 LeetCode 토론 게시판에도 "간단해 보이는데 시간 초과가 잘 난다"는 코멘트가 여럿 있는데, 정렬 기반 접근이 바로 그 함정에 걸리기 쉬운 방식이다. 작은 입력에서는 체감 차이가 없지만, 제약사항의 최댓값(`3×10^4`) 근처로 갈수록 슬라이딩 윈도우 쪽이 안전하다.
