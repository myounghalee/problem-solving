# [LeetCode 100] Same Tree — 두 트리를 동시에 내려가며 재귀로 비교하기

- 문제 번호: 100
- 링크: https://leetcode.com/problems/same-tree/
- 난이도: Easy
- 태그: Tree, DFS, BFS, Binary Tree
- 사용 자료구조/알고리즘: **재귀(DFS)**

## 1. 문제 요약

두 이진 트리 `p`, `q`가 **구조와 값 모두 완전히 같은지** 판정한다.

```text
예시) p=[1,2,3], q=[1,2,3] → true
      p=[1,2], q=[1,null,2] → false  (2의 위치가 다름 — 왼쪽 자식 vs 오른쪽 자식)
```

## 2. 접근 아이디어

### 두 트리를 "따로" 보지 말고 "동시에" 내려간다

같은 트리인지 판정하려면 결국 모든 대응 위치의 값이 같고, 어느 한쪽에만 노드가 있는 자리가 없어야 한다. 그러려면 **두 트리를 각각 훑어서 결과를 나중에 비교**하는 것보다, **두 트리를 같은 위치에서 동시에 한 걸음씩 내려가며 그 자리에서 바로 비교**하는 게 훨씬 직접적이다.

`p`와 `q`의 루트에서 시작해서, 매 단계마다 세 가지를 확인한다.

1. 둘 다 `null`인가? → 이 가지는 여기서 끝났고 서로 일치한다.
2. 한쪽만 `null`인가? → 즉시 다른 트리다.
3. 둘 다 노드가 있다면, **값이 같은지** 확인하고, **왼쪽 자식끼리, 오른쪽 자식끼리** 각각 같은 검사를 재귀로 반복한다.

```text
isSameTree(p, q) = (p, q 둘 다 null)
                  또는 (p.val == q.val
                        AND isSameTree(p.left, q.left)
                        AND isSameTree(p.right, q.right))
```

**"왼쪽은 왼쪽끼리, 오른쪽은 오른쪽끼리"라는 대응 관계를 재귀 호출 자체가 강제한다**는 점이 핵심이다. `isSameTree(p.left, q.left)`를 호출하는 순간, 그 안에서 무슨 일이 일어나든 "이건 p의 왼쪽 서브트리와 q의 왼쪽 서브트리를 비교하는 중"이라는 사실이 흔들리지 않는다.

### 손으로 시뮬레이션 — `p=[1,2,1], q=[1,1,2]`

```text
p:    1        q:    1
     / \            / \
    2   1          1   2
```

| 호출 | 비교 | 결과 |
|---|---|---|
| `isSameTree(p, q)` | `p.val(1) == q.val(1)` | 통과, 자식 비교로 진행 |
| `isSameTree(p.left=2, q.left=1)` | `2 == 1`? | **불일치 → false** |

왼쪽 자식에서 바로 `false`가 나와 전체가 `false`다. `and` 연산의 단락 평가(short-circuit) 덕분에 오른쪽 자식 비교는 실행조차 되지 않는다.

## 3. 코드 (Java)

```java
class TreeNode {
    int val;
    TreeNode left;
    TreeNode right;
    TreeNode() {}
    TreeNode(int val) { this.val = val; }
    TreeNode(int val, TreeNode left, TreeNode right) {
        this.val = val;
        this.left = left;
        this.right = right;
    }
}

class Solution {
    public boolean isSameTree(TreeNode p, TreeNode q) {
        if (p == null && q == null) return true;
        if (p == null || q == null) return false;
        return p.val == q.val && isSameTree(p.left, q.left) && isSameTree(p.right, q.right);
    }
}
```

### 코드 설명

- **두 `null` 검사의 순서가 중요하다.** `둘 다 null` → `true`를 먼저 확인하고, 그다음 `어느 한쪽만 null` → `false`를 확인한다. 이 두 줄을 통과하면 이후 코드에서는 `p`와 `q` 모두 `null`이 아님이 보장되어, `p.val`과 `q.val`에 안전하게 접근할 수 있다.
- `&&`의 단락 평가로 인해, `p.val != q.val`이면 곧바로 `false`가 되고 재귀 호출 두 개는 실행되지 않는다. 불필요한 순회를 피하는 자연스러운 최적화다.

## 4. 복잡도 분석

- **시간복잡도**: `O(min(m, n))` — `m`, `n`은 두 트리의 노드 개수. 값이 다른 지점을 만나는 즉시 중단되므로 최악의 경우(트리가 완전히 같거나, 다른 지점이 아주 늦게 나옴)에만 두 트리 전체를 다 훑는다.
- **공간복잡도**: `O(min(h1, h2))` — 재귀 호출 스택 깊이로, 두 트리 중 더 얕은 쪽의 높이에 비례한다(한쪽이 먼저 끝나면 그 이상 깊이 들어가지 않는다).

## 5. 엣지 케이스

- **둘 다 빈 트리** (`null, null`): 첫 번째 검사에서 바로 `true`.
- **한쪽만 빈 트리**: 두 번째 검사에서 바로 `false`.
- **노드 개수는 같지만 값 배치가 다름** (`[1,2,1]` vs `[1,1,2]`): 재귀가 값이 다른 첫 지점에서 바로 걸러낸다.
- **구조가 다름** (`[1,2]` vs `[1,null,2]`): `2`가 왼쪽 자식인지 오른쪽 자식인지가 다르므로, `isSameTree(p.left, q.left)`에서 `p.left=2, q.left=null`을 만나 `false`.

검증: 노드 7개 이하의 **가능한 모든 트리 모양 조합(8,558개 트리, 약 3,700만 쌍)**을 전수 비교했고, 별도로 무작위 200,000쌍을 재귀 기준 구현과 교차 검증해 전부 일치했다.

## 6. 겪었던 함정 — 레벨 순회 직렬화로 비교했더니, 서로 다른 트리가 같다고 나왔다

처음 시도한 방법은 두 트리를 각각 리스트로 직렬화한 뒤 `List.equals()`로 비교하는 것이었다. BFS로 레벨 순서대로 값을 모으되, **리프 노드는 마커를 아예 남기지 않고, 한쪽 자식만 있는 노드는 없는 쪽에 `null` 하나만 남기는** 방식이었다.

```java
if (cur.left == null && cur.right == null) continue; // 리프 → 아무것도 안 남김
if (cur.left == null) list.add(null); else { list.add(cur.left.val); queue.offer(cur.left); }
if (cur.right == null) list.add(null); else { list.add(cur.right.val); queue.offer(cur.right); }
```

준비된 예제, 무작위 100,000쌍 모두 통과했다. 하지만 **노드 7개 이하의 모든 트리 모양을 전수 비교**하자 다음과 같은 반례가 나왔다.

```text
트리 A                 트리 B
   1                      1
  / \                    / \
 2   3                  2   3
    /                  /
   4                  4

A의 직렬화 = [1, 2, 3, 4, null]
B의 직렬화 = [1, 2, 3, 4, null]   ← 완전히 같다
```

**원인은 "생략"이 위치 정보를 지운다는 데 있다.** A에서는 `2`(리프)가 아무것도 안 남기고 조용히 사라지고 `3`이 `[4, null]`을 낸다. B에서는 반대로 `3`(리프)이 조용히 사라지고 `2`가 `[4, null]`을 낸다. **누가 사라졌는지에 대한 기록이 리스트 어디에도 남지 않기 때문에**, 서로 다른 부모가 낸 `[4, null]`이 리스트 안에서 구분되지 않고 같은 자리에 나타난다.

이게 왜 무작위 테스트로는 안 잡혔을까. 이 충돌이 성립하려면 "리프 노드 하나"와 "한쪽 자식만 있는 노드 하나"가 **큐에서 정확히 이웃한 순서로 나란히 처리되면서, 서로의 순서가 뒤바뀌어도 같은 리스트가 나오는** 특정 배치가 필요하다. 무작위로 트리를 뿌리면 이런 정교한 배치가 우연히 나올 확률이 낮아서, 10만 번을 돌려도 걸리지 않았다. **전수 탐색이 무작위 테스트보다 이런 종류의 "특정 배치에서만 터지는" 버그를 훨씬 잘 잡아낸다.**

완전한 레벨 순회 직렬화(예: LeetCode가 트리를 문자열로 표현할 때 쓰는 방식)라면 **모든 non-null 노드에 대해 자식이 있든 없든 항상 두 슬롯을 남겨야** 이런 모호함이 생기지 않는다. 리프에서 마커를 생략하는 최적화가 바로 이 보장을 깨뜨린 것이다.

**교훈: 트리를 "압축된" 형태로 직렬화해서 비교하는 방식은, 그 압축이 정말로 무손실인지(서로 다른 두 트리가 같은 직렬화를 낼 수 없는지)를 증명할 수 있을 때만 안전하다.** 확신이 없다면, 3절처럼 두 트리를 직접 동시에 내려가며 비교하는 방법이 훨씬 안전하고 짧다.

## 7. 이런 방법도 있다 — 반복(iterative)으로, 스택이나 큐 하나로

재귀 대신 스택(또는 큐) 하나에 **`p`와 `q`의 대응 노드 쌍**을 함께 넣어 반복문으로 처리할 수 있다. 재귀 스택을 명시적인 자료구조로 옮긴 것뿐이라 로직은 3절과 동일하다.

```java
import java.util.*;

class Solution {
    public boolean isSameTree(TreeNode p, TreeNode q) {
        Deque<TreeNode[]> stack = new ArrayDeque<>();
        stack.push(new TreeNode[]{p, q});

        while (!stack.isEmpty()) {
            TreeNode[] pair = stack.pop();
            TreeNode a = pair[0], b = pair[1];

            if (a == null && b == null) continue;
            if (a == null || b == null || a.val != b.val) return false;

            stack.push(new TreeNode[]{a.left, b.left});
            stack.push(new TreeNode[]{a.right, b.right});
        }
        return true;
    }
}
```

핵심은 **"비교할 두 노드를 항상 쌍으로 묶어서" 자료구조에 넣는 것**이다. 6절의 실패한 방식처럼 두 트리를 각각 따로 직렬화해 나중에 비교하면 대응 관계가 유실될 수 있지만, 이 방식은 `{a, b}` 쌍 자체가 "이 둘은 서로 비교해야 할 대응 노드"라는 관계를 스택에 넣는 시점부터 끝까지 명시적으로 들고 다닌다.

**비교:**

| | 재귀 (3절) | 반복 (7절) |
|---|---|---|
| 대응 관계 유지 방법 | 함수 호출 인자(`p`, `q`)로 자연스럽게 | 배열/쌍으로 묶어서 명시적으로 |
| 추가 공간 | 호출 스택 (`O(높이)`) | 직접 만든 스택 (`O(높이)`, 최악엔 `O(노드 수)`) |
| 스택 오버플로 위험 | 트리가 매우 깊으면 가능 | 없음(힙 메모리 사용) |

이 문제는 노드가 최대 100개뿐이라 재귀 깊이 걱정이 없지만, 트리 깊이가 아주 깊어질 수 있는 문제라면 반복 버전이 스택 오버플로에서 자유롭다는 이점이 있다.
