# [LeetCode 11] Container With Most Water — 짧은 쪽만 옮기는 투 포인터

- 문제 번호: 11
- 링크: https://leetcode.com/problems/container-with-most-water/
- 난이도: Medium
- 태그: Array, Two Pointers, Greedy
- 사용 자료구조/알고리즘: **양 끝에서 좁혀오는 투 포인터**

## 1. 문제 요약

세로선 `n`개 중 두 개를 골라, 그 사이에 담을 수 있는 물의 최대량을 구한다. 담기는 양은 `min(height[i], height[j]) * (j - i)` — **짧은 쪽 높이**로 채워지고, 폭은 두 선 사이 거리다.

```text
예시) [1,8,6,2,5,4,8,3,7] → 49   (인덱스 1과 8: min(8,7)*7=49)
```

## 2. 접근 아이디어

### 모든 쌍을 보면 `O(n²)`, `n ≤ 10^5`라 시간 초과

두 선을 고르는 모든 조합을 브루트포스로 보면 `O(n²)`이라 통과하지 못한다. `O(n)`으로 줄여야 한다.

### 가장 넓은 폭에서 시작해, 짧은 쪽만 안으로 옮긴다

양 끝(`left=0`, `right=n-1`)에서 시작한다. 이게 **가능한 최대 폭**이다. 이후 두 포인터를 안으로 좁혀가는데, **매 순간 둘 중 더 짧은 쪽만 옮긴다.**

왜 짧은 쪽만 옮기면 되는지가 이 문제의 핵심이다. 지금 `height[left] < height[right]`라고 하자. `left`가 물의 높이를 결정하는 쪽(짧은 쪽)이다.

- **`right`를 옮기면**: 폭이 줄어든다. 그런데 새 높이는 `min(height[left], height[새 right])`인데, `height[left]`가 이미 원래 두 값 중 더 작았으므로, 새 높이는 **절대 `height[left]`보다 커질 수 없다.** 즉 높이는 그대로거나 더 작아지고, 폭은 확실히 줄었다. **손해만 본다.**
- **`left`를 옮기면**: 폭은 똑같이 줄지만, 높이가 `height[left]`보다 커질 **가능성**이 있다(더 큰 값을 만날 수도 있으니). 손해를 볼 수도 있지만 적어도 **개선의 여지**가 있다.

그래서 "지금보다 나빠질 게 확실한 선택"(긴 쪽 옮기기)은 절대 하지 않고, "나아질 가능성이 있는 선택"(짧은 쪽 옮기기)만 한다. 이렇게 하면 가능한 모든 "진짜 최적일 수 있는" 쌍을 하나도 건너뛰지 않고 `O(n)`에 전부 훑을 수 있다.

### 손으로 시뮬레이션 — `[1,8,6,2,5,4,8,3,7]`

| `left` | `right` | 넓이 | 최댓값 | 다음 동작 |
|---|---|---|---|---|
| 0(`1`) | 8(`7`) | `min(1,7)*8=8` | 8 | `height[0]=1 < height[8]=7` → `left++` |
| 1(`8`) | 8(`7`) | `min(8,7)*7=49` | **49** | `height[1]=8 > height[8]=7` → `right--` |
| 1(`8`) | 7(`3`) | `min(8,3)*6=18` | 49 | `right--` |
| 1(`8`) | 6(`8`) | `min(8,8)*5=40` | 49 | 둘이 같으면 관례적으로 한쪽(여기선 `right`)을 옮김 |
| ... | | | 49 | (이후로도 49를 넘지 못함) |

정답 `49`가 두 번째 단계에서 이미 발견되고, 이후로는 갱신되지 않는다.

## 3. 코드 (Java)

```java
class Solution {
    public int maxArea(int[] height) {
        int max = 0;
        int left = 0, right = height.length - 1;

        while (left < right) {
            max = Math.max(max, (right - left) * Math.min(height[left], height[right]));
            if (height[left] < height[right]) left++;
            else right--;
        }

        return max;
    }
}
```

### 코드 설명

- `max`를 매 단계 갱신한다 — 두 포인터가 좁혀지는 동안 만나는 모든 "짧은 쪽만 옮긴" 쌍이 최적의 후보이므로, 그중 최댓값만 계속 추적하면 된다.
- `height[left] < height[right]`일 때 `left++`, 아니면(같거나 `right`가 더 짧을 때) `right--`. 둘이 같을 때 어느 쪽을 옮겨도 정답에는 영향이 없다 — 같은 높이라면 어느 쪽을 짧은 쪽으로 보든 위 논증이 동일하게 성립한다.
- `left < right`가 종료 조건이다. 둘이 만나면 더 이상 고를 수 있는 쌍이 없다.

## 4. 복잡도 분석

- **시간복잡도**: `O(n)` — `left`와 `right`가 서로를 향해 한 칸씩만 움직이고, 총 이동 횟수는 `n`을 넘지 않는다.
- **공간복잡도**: `O(1)` — 변수 몇 개뿐.

실측: 제약 상한(`n=100,000`)에서 0ms.

## 5. 엣지 케이스

- **선이 둘뿐** (`[1,1]`): 첫 반복에서 바로 답이 정해지고 루프가 끝난다.
- **가장 큰 두 선이 양 끝에 있지 않은 경우** (`[1,2,1]`): 양 끝(`1`,`1`)에서 시작해도, 짧은 쪽을 옮겨가며 안쪽의 `2`까지 정확히 탐색된다.
- **오름차순 배열** (`[1,2,3,4,5]`): 가장 넓은 폭(양 끝, `min(1,5)*4=4`)이 정답이 아닌 대표 사례. 정답은 `min(2,5)*3=6`(인덱스 1과 4) — **폭이 가장 넓다고 답이 되는 건 아니다.**
- **모두 같은 높이** (`[4,4,4,4,4]`): 높이가 항상 `4`로 고정이니, 폭이 가장 넓은 양 끝을 쓰는 게 곧 최댓값이다.

검증: 무작위 20,000건(값 범위를 좁혀 동점 케이스를 자주 만듦)을 브루트포스와 교차 비교해 전부 일치했다.

## 6. 관련 문제

같은 **양 끝에서 좁혀오는 투 포인터** 계열이지만, "무엇을 찾느냐"가 다르다.

- [Valid Palindrome (LeetCode 125)](../125-valid-palindrome/Solution.md) — 같은 뼈대(양 끝에서 안으로)를 쓰지만, 값을 최적화하는 게 아니라 **대칭 여부를 판정**한다. 이 문제는 "둘 중 뭘 옮길지"를 판단해야 하는 반면, 그쪽은 "다르면 즉시 실패"로 끝난다는 점이 대비된다.
- [3Sum (LeetCode 15)](../15-3sum/Solution.md) — 정렬된 배열에서 두 값의 합이 목표치와 같은지를 찾는 투 포인터. 이 문제는 "합이 특정 값인가"가 아니라 "곱(넓이)이 최대인가"를 본다는 점에서, 옮길 방향을 정하는 논리가 다르다(그쪽은 합의 크기 비교, 이 문제는 "짧은 쪽이 항상 손해"라는 논증).
