# [LeetCode 15] 3Sum — 하나를 고정해 2Sum(투 포인터)으로 축소하기

- 문제 번호: 15
- 링크: https://leetcode.com/problems/3sum/
- 난이도: Medium
- 태그: Array, Two Pointers, Sorting
- 사용 자료구조/알고리즘: **정렬 + 투 포인터**

## 1. 문제 요약

정수 배열 `nums`에서 **합이 0이 되는 서로 다른 세 수의 조합**을 값 기준으로 중복 없이 전부 찾는다.

```text
예시) [-1,0,1,2,-1,-4] → [[-1,-1,2],[-1,0,1]]
```

배열에 `-1`이 두 번 있어도, 값이 같은 조합은 한 번만 나와야 한다.

## 2. 접근 아이디어

### `k`개를 더하는 문제는 하나를 고정하면 `k-1`개짜리 문제가 된다

3Sum을 브루트포스로 풀면 세 수를 모두 자유롭게 고르는 `O(n^3)`이다. 제약이 `n ≤ 3000`이라 이건 시간 초과다.

핵심은, **세 수 중 하나(`nums[i]`)를 고정하면 남은 문제가 "합이 `-nums[i]`가 되는 두 수 찾기"**, 즉 2Sum이 된다는 점이다. 그리고 [167번(Two Sum II)](../167-two-sum-ii-input-array-is-sorted/Solution.md)에서 이미 다뤘듯, **정렬된 배열에서 2Sum은 투 포인터로 `O(n)`에 풀린다.**

```text
바깥 루프: i를 0부터 n-3까지 고정          → O(n)
안쪽:     정렬된 [i+1, n-1] 구간에서
          합이 -nums[i]인 두 수를 투 포인터로 탐색 → O(n)
```

`O(n) × O(n) = O(n^2)`. 정렬(`O(n log n)`)은 여기 묻힌다.

### 정렬이 왜 방향을 확신하게 해주는가

투 포인터가 "합이 작으면 `left`를 옮기고, 크면 `right`를 옮긴다"는 판단을 하려면, "왼쪽으로 가면 커진다/작아진다"는 방향이 확실해야 한다. 정렬되어 있어야만 이 방향이 항상 참이고, 그래서 후보를 하나도 빠뜨리지 않고 `O(n)`에 전부 훑을 수 있다. 정렬 안 된 배열이면 이 전략 자체가 성립하지 않는다.

### 손으로 시뮬레이션 — 정렬 후 `[-4, -1, -1, 0, 1, 2]`

**`i=0`** (`nums[i]=-4`, 목표 `4`): `left=1, right=5`

| left | right | 합 | 비교 | 동작 |
|---|---|---|---|---|
| -1 | 2 | 1 | `<4` | `left++` |
| -1 | 2 | 1 | `<4` | `left++` |
| 0 | 2 | 2 | `<4` | `left++` |
| 1 | 2 | 3 | `<4` | `left++` (`left==right`, 종료) |

`-4`는 짝을 못 찾고 끝난다.

**`i=1`** (`nums[i]=-1`, 목표 `1`): `left=2, right=5`

| left | right | 합 | 비교 | 동작 |
|---|---|---|---|---|
| -1 | 2 | 1 | `==1` | **`(-1,-1,2)` 발견!** `left++, right--` |
| 0 | 1 | 1 | `==1` | **`(-1,0,1)` 발견!** `left++, right--` (종료) |

**`i=2`**: `nums[2]=-1 == nums[1]`이므로 건너뛴다(안 그러면 `(-1,-1,2)`가 또 나온다).

**`i=3`**(`nums[i]=0`)부터는 남은 구간이 두 칸뿐이라 `left < right`가 곧 깨져 답이 없다.

결과: `[(-1,-1,2), (-1,0,1)]` — 정답과 일치한다.

### 중복을 걸러야 하는 세 자리

값 기준으로 같은 조합이 여러 번 나오지 않게 하려면, 정렬된 배열에서 "이전과 같은 값"을 세 곳에서 건너뛰어야 한다.

1. **바깥 루프의 `i`**: `nums[i] == nums[i-1]`이면 건너뛴다. 안 그러면 같은 `i`로 시작하는 스캔을 통째로 반복하게 된다.
2. **조합을 찾은 뒤의 `left`**: 다음 `nums[left]`가 방금 것과 같으면 또 건너뛴다.
3. **같은 순간의 `right`**: 다음 `nums[right]`가 같으면 건너뛴다.

## 3. 코드 (Java)

```java
import java.util.*;

class Solution {
    public List<List<Integer>> threeSum(int[] nums) {

        Arrays.sort(nums);
        List<List<Integer>> lists = new ArrayList<>();

        for (int i = 0; i < nums.length - 2; i++) {
            if (i > 0 && nums[i] == nums[i - 1]) continue; // i 중복 스킵
            int left = i + 1, right = nums.length - 1;

            while (left < right) {
                if (nums[left] + nums[right] + nums[i] == 0) {
                    lists.add(Arrays.asList(nums[i], nums[left], nums[right]));
                    while (left < right && nums[left] == nums[left + 1]) left++;   // left 중복 스킵
                    while (left < right && nums[right] == nums[right - 1]) right--; // right 중복 스킵
                    left++;
                    right--;
                } else if (nums[left] + nums[right] + nums[i] < 0) {
                    left++;
                } else {
                    right--;
                }
            }
        }

        return new ArrayList<>(lists);
    }
}
```

### 코드 설명

- `Arrays.sort(nums)`가 투 포인터와 중복 스킵 둘 다의 전제 조건이다.
- `i > 0 && nums[i] == nums[i-1]`: `i=0`일 때는 비교할 이전 값이 없으므로 `i > 0`을 먼저 확인한다.
- `lists.add(Arrays.asList(...))`: 세 개의 `int`를 개별 인자로 넘기면 오토박싱되어 **새 `Integer[]` 배열**이 만들어지므로, `nums` 원본을 참조하지 않는다. 세 군데 스킵이 정확해서 중복이 애초에 생기지 않기 때문에, `HashSet`으로 다시 거를 필요 없이 곧바로 `ArrayList`에 쌓는다(6·7절 참고 — 처음부터 이 형태였던 것은 아니다).
- **조합을 찾은 뒤 `left`/`right` 스킵을 먼저 하고 그다음 `left++, right--`를 한다.** 순서를 반대로 하면(먼저 `++`/`--` 하고 스킵) 정확히 한 칸씩 어긋난 값을 비교하게 되어 스킵이 제대로 동작하지 않는다.

## 4. 복잡도 분석

- **시간복잡도**: `O(n^2)` — 정렬 `O(n log n)`, 바깥 `i` 루프 `O(n)`, 각 `i`마다 투 포인터가 `O(n)`. `i` 스킵은 반복 횟수를 줄여줄 뿐 최악의 경우(모든 값이 서로 다름)엔 여전히 `O(n^2)`.
- **공간복잡도**: `Arrays.sort`의 내부 구현에 따라 `O(log n)`(기본 타입 배열의 듀얼 피벗 퀵정렬)이 추가로 들고, 결과를 담는 공간은 출력 크기에 비례한다.

실측(`n=3000`, 무작위, 워밍업 후): 정렬 후 메인 루프에 11ms.

## 5. 엣지 케이스

- **길이가 정확히 3**: `i=0` 한 번만 돈다.
- **모두 같은 값** (`[0,0,0]`): 셋의 합이 0이면 `i` 스킵이 나머지 반복을 대부분 걸러낸다.
- **답이 없는 경우** (`[0,1,1]`): 투 포인터가 끝까지 돌아도 `sum==0`을 못 찾고 빈 리스트를 반환한다.
- **같은 값이 여러 개, 조합도 여러 번 나올 수 있는 배열** (`[-2,0,0,2,2]`): 세 스킵이 없으면 `(-2,0,2)`가 인덱스 조합만 바꿔가며 여러 번 나온다.

검증: 무작위 20,000건(값 범위를 좁혀 중복을 자주 만듦)을 브루트포스(세 중첩 루프 + `Set`으로 중복 제거)와 교차 비교해 전부 일치했다.

## 6. 겪었던 함정들

이 문제를 푸는 과정에서 실제로 세 단계의 시행착오를 거쳤다. 각각 남겨둘 값어치가 있다.

### (1) `HashSet<int[]>`로 중복을 걸렀더니 중복이 그대로 남았다

가장 먼저 떠오른 방법은 세 중첩 루프로 모든 조합을 찾고 `Set`으로 중복을 거르는 것이었다.

```java
Set<int[]> set = new HashSet<>();
...
int[] arr = {nums[i], nums[j], nums[k]};
Arrays.sort(arr);
set.add(arr);
```

결과에 `[-1, 0, 1]`이 두 번, `[-2, 0, 2]`가 네 번 들어 있었다. **배열(`int[]`)은 `Object`의 기본 `equals`/`hashCode`를 그대로 쓰는데, 이건 내용이 아니라 객체 주소를 비교한다.** 내용이 완전히 같은 두 배열도 `new`로 만들 때마다 별개의 객체라서 `HashSet`이 서로 다른 원소로 취급한다.

```java
int[] a = {-1, 0, 1};
int[] b = {-1, 0, 1};
a.equals(b);   // false
```

`int[]` 대신 `List<Integer>`로 바꾸면 해결된다. `List`의 `equals`/`hashCode`는 **원소를 순서대로 비교**하도록 오버라이드되어 있어서, 값이 같은 리스트는 정확히 같다고 판정된다.

**교훈: `HashSet`/`HashMap`에 배열을 키로 쓰면 안 된다.** 내용 비교가 필요하면 `List`나 `equals`/`hashCode`를 오버라이드한 타입을 써야 한다.

### (2) 정답은 맞지만, 찾은 걸 또 찾고 버리느라 느렸다

`List`로 바꾸고 `O(n^2)` 투 포인터로 넘어온 뒤, `n=3000` 무작위 입력에서 151ms가 나왔다. 순수 투 포인터 이동 자체만 떼어 재보면 10ms였다 — 나머지 141ms가 어디서 새는지 찾아야 했다.

```text
sum==0으로 성공한 횟수 = 629,503번
실제 유니크한 답     = 238,951개
→ 390,552번은 이미 찾은 조합을 또 찾아서 버리는 헛수고
```

`left`/`right`의 이웃 중복을 건너뛰지 않으니, 같은 값 조합을 최대 62%나 다시 만들고 있었다. 그리고 "다시 만드는" 비용이 싸지 않았다 — `Arrays.asList`로 객체 생성, `Collections.sort`(또는 매번 정렬된 상태로 넣기), `HashSet.add`의 해싱과 충돌 처리까지 629,503번 전부에 대해 반복됐다.

`left`/`right` 스킵을 넣자 65ms로 줄었지만, 그래도 기대만큼은 아니었다. 원인은 다음 함정에 있었다.

### (3) 바깥 루프 `i`의 중복을 놓쳐서, 절반 가까운 반복이 통째로 낭비됐다

```text
바깥 루프 i 반복 횟수 = 2998
그중 이전 i와 값이 같아 건너뛸 수 있는 것 = 1435   ← 48%
```

`nums[i]`가 이전과 같으면, 그 `i`로 도는 투 포인터 스캔은 **이전 `i`가 이미 찾은 것과 완전히 똑같은 조합**을 처음부터 다시 찾는다. 안쪽에서 `left`/`right`를 아무리 건너뛰어도, 바깥에서 매번 같은 시작점부터 다시 스캔하니 그 자체가 반복 작업이다.

```java
if (i > 0 && nums[i] == nums[i - 1]) continue;
```

이 한 줄을 추가하자 `set.add` 호출이 453,628번에서 238,951번(정확히 유니크한 개수)으로 줄었고, 시간은 65ms → 47ms가 되었다.

**교훈: 중복을 걸러야 하는 자리가 여러 개(고정값, 두 포인터)일 때는, 그중 하나만 막고 "이 정도면 됐겠지" 하고 넘어가기 쉽다.** 각 자리에서 "이걸 안 막으면 정확히 어떤 반복 작업이 생기는가"를 따로 확인해야 놓치는 자리가 안 남는다. 실측(반복 횟수, `set.add` 호출 횟수)으로 확인하지 않았다면 `i` 스킵 누락은 눈치채기 어려웠을 것이다 — 정답 자체는 `Set`이 어차피 걸러주므로 틀리지 않기 때문이다.

## 7. 이렇게도 시작할 수 있다 — 처음엔 `HashSet`으로 안전하게

실제로 이 풀이는 처음부터 3절의 `List` 버전이 아니었다. 스킵 로직 세 군데(`i`, `left`, `right`)를 손으로 검증하기가 까다로워서, 처음엔 `HashSet<List<Integer>>`을 안전망으로 두고 시작했다.

```java
Set<List<Integer>> set = new HashSet<>();
...
if (nums[left] + nums[right] + nums[i] == 0) {
    set.add(Arrays.asList(nums[i], nums[left], nums[right]));
    ...
}
...
return new ArrayList<>(set);
```

이 버전은 스킵 로직에 실수가 있어도(예: `left`/`right` 스킵을 깜빡했다거나) **결과가 틀리지 않는다** — 중복이 생기면 `Set`이 그냥 걸러준다. 대신 그만큼 느리다.

**단계별로 걷어내며 측정한 값** (`n=3000`, 워밍업 후):

| | `left`/`right`만 스킵 + `Set` | `i`까지 스킵 + `Set` | `i`까지 스킵 + `Set` 없이 `List`(현재 3절) |
|---|---|---|---|
| 시간 | 65ms | 47ms | **11ms** |
| `set.add`/`list.add` 호출 | 453,628번 | 238,951번(=유니크 개수) | 238,951번 |

세 스킵이 전부 정확해지고 나서야(즉 애초에 중복이 생기지 않는다는 확신이 선 뒤에야) `Set`을 걷어내고 `ArrayList`로 바꿨다. `Set`을 걷어내면 `List`의 `hashCode()` 계산, 해시 충돌 처리, 테이블 리사이즈 비용이 통째로 사라진다 — `i`까지 스킵한 상태에서도 47ms → 11ms로 4배 넘게 차이 난다. 이 마지막 구간의 차이는 알고리즘이 아니라 **자료구조 선택**(해싱 vs 단순 추가)에서 온다.

**교훈: 중복 제거 로직이 복잡할 때는 "정답이 확실히 맞는(느린) 버전"을 먼저 만들고 무작위 테스트로 충분히 검증한 뒤, 그 검증된 로직을 근거로 안전망(`Set`)을 걷어내는 순서가 안전하다.** 처음부터 최적화된 형태로 짜면, 결과가 우연히 맞아떨어져도 스킵 로직 자체의 오류를 잡아낼 방법이 없다.
