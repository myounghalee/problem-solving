# [LeetCode 80] Remove Duplicates from Sorted Array II — 읽기/쓰기 포인터로 제자리 압축하기

- 문제 번호: 80
- 링크: https://leetcode.com/problems/remove-duplicates-from-sorted-array-ii/
- 난이도: Medium
- 태그: Array, Two Pointers
- 사용 자료구조/알고리즘: **투 포인터(읽기/쓰기 포인터)**

## 1. 문제 요약

정렬된 배열 `nums`에서 같은 값이 **최대 두 번까지만** 남도록 중복을 제거한다. 단, 새 배열을 만드는 게 아니라 **`nums` 자체를 제자리(in-place)에서 수정**해야 하고, 유효한 원소 개수 `k`를 반환한다. 채점기는 `nums`의 앞 `k`개만 확인한다.

```text
예시) nums = [1,1,1,2,2,3] → k=5, nums 앞 5칸 = [1,1,2,2,3]
      nums = [0,0,1,1,1,1,2,3,3] → k=7, nums 앞 7칸 = [0,0,1,1,2,3,3]
```

## 2. 접근 아이디어

`HashMap`으로 각 값의 등장 횟수를 세는 방법도 개수(`k`)는 맞게 구할 수 있지만, (1) `nums` 자체를 덮어쓰지 않으므로 결과 배열이 안 만들어지고, (2) 서로 다른 값의 개수만큼 공간을 쓰므로 `O(n)` 공간이 든다 — 이 문제가 요구하는 `O(1)` 공간 제약을 어긴다.

배열이 **정렬돼 있다**는 조건을 쓰면, 같은 값은 항상 연속된 구간에 뭉쳐 있다. 그래서 굳이 값별로 세지 않아도, **바로 앞의 값과 몇 번 연속됐는지만** 기억하면 충분하다. 이를 위해 두 개의 포인터를 쓴다.

- **읽기 포인터 `right`**: 배열을 처음부터 끝까지 한 칸씩 훑는다.
- **쓰기 포인터 `left`**: 지금까지 "살아남은" 값들을 앞에서부터 다시 채워 넣을 위치를 가리킨다.
- `num`(현재 보고 있는 값)과 `numCount`(그 값이 몇 번 연속됐는지)를 유지하다가:
  - `nums[right]`가 `num`과 같고 `numCount`가 이미 `2`면 → 세 번째 이상 등장한 중복이므로 **건너뛴다**(아무것도 안 함, `right`만 다음으로).
  - 그 외의 경우(새로운 값이거나, 아직 2번째 등장) → 유효한 값이므로 `nums[left]`에 써넣고 `left`, `count`를 하나 늘린다.

`left`는 항상 `right`보다 작거나 같으므로(지금까지 읽은 개수 ≥ 지금까지 써넣은 개수), 아직 안 읽은 값을 덮어쓸 위험이 없다 — 그래서 별도 배열 없이 `nums` 하나로 안전하게 처리된다.

### 손으로 시뮬레이션 — `nums = [1, 1, 1, 2, 2, 3]`

| right | nums[right] | 이전 num / numCount | 판단 | 동작 | left(쓴 후) | count |
|---|---|---|---|---|---|---|
| 0 | 1 | MIN_VALUE / 1 | 새 값 | `num=1, numCount=1`, `nums[0]=1` | 1 | 1 |
| 1 | 1 | 1 / 1 | 2번째 등장 | `numCount=2`, `nums[1]=1` | 2 | 2 |
| 2 | 1 | 1 / 2 | 3번째 등장(초과) | 건너뜀 | 2 | 2 |
| 3 | 2 | 1 / 2 | 새 값 | `num=2, numCount=1`, `nums[2]=2` | 3 | 3 |
| 4 | 2 | 2 / 1 | 2번째 등장 | `numCount=2`, `nums[3]=2` | 4 | 4 |
| 5 | 3 | 2 / 2 | 새 값 | `num=3, numCount=1`, `nums[4]=3` | 5 | 5 |

결과: `nums`의 앞 5칸이 `[1, 1, 2, 2, 3]`, `count=5` — 정답과 일치한다.

## 3. 코드 (Java)

```java
class Solution {
    public int removeDuplicates(int[] nums) {
        int count = 0;                // 유효한 원소 개수(반환값)
        int left = 0;                 // 쓰기 포인터 - 다음에 값을 써넣을 위치
        int num = Integer.MIN_VALUE;  // 현재 추적 중인 값(시작 sentinel)
        int numCount = 1;             // num이 연속으로 몇 번 등장했는지
        for (int right = 0, numsLength = nums.length; right < numsLength; right++) { // 읽기 포인터
            if (num == nums[right]) {
                if (numCount >= 2) continue; // 세 번째 이상 중복 -> 건너뛴다
                numCount++;
            } else {
                numCount = 1;   // 새로운 값 -> 카운트 초기화
                num = nums[right];
            }

            count++;
            nums[left++] = nums[right]; // 유효한 값만 앞으로 당겨서 덮어쓴다
        }
        return count;
    }
}
```

### 코드 설명

- `right`는 배열 전체를 한 번만 훑는 읽기 포인터, `left`는 결과를 채워나가는 쓰기 포인터다. 둘 다 `nums` 안에서만 움직이므로 추가 배열이 없다.
- `num`/`numCount`는 "직전에 본 값과 그 연속 횟수"만 기억한다. 배열이 정렬돼 있어 같은 값이 항상 뭉쳐 나오므로, 값별로 전체 개수를 셀 필요 없이 **연속 횟수가 2를 넘는 순간만** 걸러내면 충분하다.
- `numCount >= 2`일 때의 `continue`는 `left`를 건드리지 않고 `right`만 다음 칸으로 넘어가게 한다 — 이게 곧 "세 번째 이상 중복을 버린다"는 동작이다.
- `nums[left++] = nums[right]`는 항상 `left <= right`인 상태에서 실행되므로, 아직 읽지 않은 값을 덮어쓸 일이 없다.

## 4. 복잡도 분석

- **시간복잡도**: `O(n)` — 배열을 한 번만 순회한다.
- **공간복잡도**: `O(1)` — `count`, `left`, `num`, `numCount` 등 변수 몇 개만 쓰고, 입력 크기에 비례하는 추가 자료구조가 없다.

앞서 시도했던 `HashMap` 풀이는 서로 다른 값의 개수만큼 키가 늘어나 최악의 경우 `O(n)` 공간을 썼다(게다가 `nums` 자체를 수정하지도 않아 결과 배열을 만들지 못했다). 정렬 조건을 활용한 읽기/쓰기 포인터 방식으로 **공간을 `O(1)`로 줄이면서 in-place 수정 요구사항까지 함께 만족**시킨 것이 이 풀이의 핵심이다.

## 5. 엣지 케이스

- **배열 길이가 1**: 루프 한 번만 돌고 `count=1`로 그대로 반환된다.
- **모든 원소가 동일**(`[2,2,2,2]`): 앞의 2개만 남고 나머지는 전부 건너뛰어 `count=2`.
- **모든 원소가 서로 다름**(`[1,2,3,4]`): `numCount`가 2에 도달하는 일이 없어 전부 그대로 남는다.
- **값의 극값**(`nums[i] = -10^4` 또는 `10^4`): 시작 sentinel이 `Integer.MIN_VALUE`이므로, 제약사항 범위(`-10^4 ~ 10^4`) 안에서는 첫 원소와 sentinel이 우연히 같아질 일이 없다.

## 6. 관련 문제

정렬된 배열 + `O(1)` 공간이라는 조건은 같지만, 포인터를 움직이는 방식이 다른 문제.

- [Two Sum II - Input Array Is Sorted (LeetCode 167)](../167-two-sum-ii-input-array-is-sorted/Solution.md) — 이 문제와 마찬가지로 "정렬된 배열 + `O(1)` 공간"이 핵심 제약이지만, 포인터가 배열 **양 끝에서 서로를 향해** 좁혀오는 방식이라, 이 문제의 "한쪽에서 훑으며 같은 자리에 덮어쓰는" 읽기/쓰기 포인터와는 동작 방식이 다르다.
