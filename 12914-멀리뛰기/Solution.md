# [프로그래머스 12914] 멀리 뛰기 — DP로 지수 시간 재귀를 O(n)으로

- 문제 번호: 12914
- 링크: https://school.programmers.co.kr/learn/courses/30/lessons/12914
- 분류: 연습문제
- 사용 자료구조/알고리즘: **DP (동적 계획법)**, 점화식
- 난이도 체감: Lv.1~2 (점화식 자체는 쉽지만, 순수 재귀로 짜면 시간 초과 함정이 있음)

## 1. 문제 요약

한 번에 1칸 또는 2칸을 뛸 수 있을 때, `n`칸에 도달하는 방법의 수를 구한다. 답이 매우 커질 수 있어서 `1234567`로 나눈 나머지를 반환한다.

```text
n=4 → 5가지: (1,1,1,1) (1,2,1) (1,1,2) (2,1,1) (2,2)
n=3 → 3가지: (2,1) (1,2) (1,1,1)
```

**제한사항**: `n`은 1 이상 2,000 이하의 정수.

## 2. 접근 아이디어 — 마지막 한 걸음으로 나누기

`n`칸에 도달하는 방법의 수를 `f(n)`이라 하면, **마지막으로 뛴 걸음이 1칸이었는지 2칸이었는지**로 전체 경우를 두 그룹으로 완전히 나눌 수 있다.

- 마지막이 1칸이었다면, 그 직전까지는 `(n-1)`칸에 도달한 것 → `f(n-1)`가지
- 마지막이 2칸이었다면, 그 직전까지는 `(n-2)`칸에 도달한 것 → `f(n-2)`가지

두 경우는 겹치지 않으므로 `f(n) = f(n-1) + f(n-2)`. 기저 조건은 `f(1) = 1` (한 칸을 1칸씩 뛰는 방법 하나뿐), `f(2) = 2` ((1,1) 또는 (2)).

**이건 [피보나치 수(12945)](../12945-피보나치수/Problem.md)와 완전히 같은 점화식**이다. 표준 피보나치를 `F(0)=0, F(1)=1, F(2)=1, F(3)=2, F(4)=3, F(5)=5, F(6)=8`로 정의하면, 이 문제의 `f(n)`은 정확히 `F(n+1)`과 같다 (`f(1)=1=F(2)`, `f(2)=2=F(3)`, `f(3)=3=F(4)`, `f(4)=5=F(5)`, `f(5)=8=F(6)`). "마지막 한 걸음으로 경우를 나눈다"는 점화식이 나오면 십중팔구 피보나치류라는 걸 알아두면 다음에도 바로 알아챌 수 있다.

### 왜 순수 재귀는 안 되는가 (+ 실제로 시간 초과가 남을 실측)

점화식만 보고 아래처럼 그대로 재귀로 옮기고 싶어질 수 있다.

```java
// 시간 초과 나는 버전 — 절대 이대로 제출하면 안 됨
public long solution(int n) {
    if (n == 1) return 1;
    if (n == 2) return 2;
    return solution(n - 1) + solution(n - 2);
}
```

이 코드는 `n=3`, `n=4` 같은 예시는 정확히 맞춘다. 하지만 **같은 부분 문제를 지수적으로 중복 계산**하는 게 문제다. `f(5)`를 구하려면 `f(4)`와 `f(3)`을 구해야 하는데, `f(4)`를 구하는 과정에서도 내부적으로 `f(3)`을 처음부터 또 구한다 — 트리로 그리면 매 레벨마다 호출이 대략 2배씩 늘어나는 `O(φⁿ)` (φ ≈ 1.618, 황금비) 구조다.

실제로 이 버전에 호출 횟수를 세는 카운터를 붙여서 측정한 결과다 (n이 커질수록 호출 횟수와 시간이 얼마나 빠르게 폭발하는지 확인):

| n | 결과값 | 재귀 호출 횟수 | 실행 시간 |
|---|---|---|---|
| 20 | 10,946 | 13,529 | 0.1ms |
| 30 | 1,346,269 | 1,664,079 | 1.6ms |
| 35 | 14,930,352 | 18,454,929 | 20.4ms |
| 38 | 63,245,986 | 78,176,337 | 76.8ms |
| 40 | 165,580,141 | 204,668,309 | 189.1ms |

`n`이 10 늘어날 때마다 호출 횟수가 약 100배씩 뛰는 게 보인다 (φ¹⁰ ≈ 123). 이 추세를 그대로 연장하면:

- `n = 100`이면 이론상 수만 년 단위의 시간이 필요하다.
- `n = 2,000`(이 문제의 실제 상한)이면 걸리는 시간이 우주의 나이보다 압도적으로 크다 — **사실상 영원히 끝나지 않는다고 봐도 무방**하다.

프로그래머스 채점 시간 제한(보통 1초 안팎)을 기준으로 보면, 이 재귀 버전은 이미 `n = 40`대 초반부터 시간 초과가 나기 시작해서 `n = 2,000`까지 가는 건 불가능하다.

덧붙여, 시간 문제를 논외로 하더라도 이 버전엔 `% 1234567` 나머지 처리가 빠져 있어서, 만에 하나 끝까지 계산된다 해도 `long`이 표현 가능한 범위(약 9.2×10¹⁸)를 `n`이 92 근처만 넘어가도 초과해 조용히 잘못된 값을 반환하게 된다. 즉 느린 것과 별개로 **정확성 자체도 깨져 있는 코드**다.

**재귀 호출 자체를 없애고 아래에서 위로 값을 쌓아 올리는 반복문(bottom-up DP)**으로 바꿔야 이 모든 문제가 `O(n)` 한 방에 해결된다.

### 손으로 시뮬레이션 — `n = 4`

반복문은 `prev2 = f(1)`, `prev1 = f(2)`에서 시작해 `i = 3`부터 `n`까지 한 칸씩 밀어 올린다.

| i | 계산 | prev2 (f(i-2)) | prev1 (f(i-1) → f(i)) |
|---|---|---|---|
| 시작 | - | 1 (`f(1)`) | 2 (`f(2)`) |
| 3 | `(2+1) % MOD = 3` | 2 | 3 (`f(3)`) |
| 4 | `(3+2) % MOD = 5` | 3 | 5 (`f(4)`) |

루프가 끝난 시점의 `prev1`이 곧 `f(4) = 5`. 예상과 일치한다.

## 3. 코드 (Java)

```java
class Solution {
    private static final int MOD = 1234567;

    public long solution(int n) {
        if (n == 1) return 1;
        if (n == 2) return 2;

        long prev2 = 1; // f(1)
        long prev1 = 2; // f(2)
        for (int i = 3; i <= n; i++) {
            long current = (prev1 + prev2) % MOD;
            prev2 = prev1;
            prev1 = current;
        }
        return prev1;
    }
}
```

### 코드 설명

- 배열에 `f(1)`부터 `f(n)`까지 전부 저장하지 않고, **직전 두 값(`prev2`, `prev1`)만 변수로 유지**한다. 다음 값을 구하는 데 그 이전 두 값만 있으면 충분하기 때문 — 배열을 쓰면 `O(n)` 공간이지만 이렇게 하면 `O(1)` 공간으로 줄어든다.
- `(prev1 + prev2) % MOD`처럼 **매 단계마다 나머지 연산을 적용**한다. 나머지를 끝에 한 번만 취하면 그 전에 `long` 범위를 넘어서는 값이 만들어질 수 있어(실제 피보나치 수는 n=2000쯤 되면 자릿수가 수백 자리) 계산이 틀어진다. 매 단계 나머지를 취해도 최종 결과(나머지)는 수학적으로 동일하다 (모듈러 연산의 분배 법칙).

## 4. 복잡도 분석

- **시간복잡도**: `O(n)` — 반복문 한 번.
- **공간복잡도**: `O(1)` — 변수 2개만 사용.

순수 재귀(`O(2ⁿ)`)와 비교하면 `n = 2000`에서 체감이 극단적으로 다르다: DP 버전은 아래처럼 즉시(0ms) 끝나지만, 순수 재귀는 사실상 끝나지 않는다.

```text
n=2000 -> 694725 (0ms)
```

## 5. 엣지 케이스

- `n = 1`, `n = 2`: 반복문에 들어가지 않고 기저 조건으로 바로 반환.
- `n = 2000` (최댓값): 위 실측대로 문제 없이 즉시 처리됨.
