# [프로그래머스 42885] 구명보트 — 탐욕법 + 투 포인터

- 문제 번호: 42885
- 링크: https://school.programmers.co.kr/learn/courses/30/lessons/42885
- 분류: 탐욕법(Greedy)
- 사용 자료구조/알고리즘: **정렬 + 투 포인터**
- 난이도 체감: Lv.2 (탐욕법이 왜 최적인지 논리를 세우는 게 핵심)

## 1. 문제 요약

구명보트 하나에 최대 2명, 무게 제한 `limit`. 사람들의 몸무게 배열 `people`이 주어질 때, 모두 구출하는 데 필요한 최소 보트 개수를 구한다.

```text
people = [70, 50, 80, 50], limit = 100 → 3
(2번+4번 = 50+50 = 100 같이 탑승, 1번·3번은 각자 보트)
```

**제한사항**: 사람 수 1~50,000명, 몸무게/제한 40~240kg. 제한은 항상 최대 몸무게보다 커서 구출 불가능한 경우는 없음.

## 2. 접근 아이디어 — 가장 무거운 사람 + 가장 가벼운 사람

몸무게로 정렬한 뒤, **가장 무거운 사람과 가장 가벼운 사람을 짝지을 수 있는지**부터 확인하는 탐욕법(Greedy)이 정석이다.

- 같이 탈 수 있으면(`가벼운 + 무거운 ≤ limit`) → 둘을 한 보트에 태우고, 양쪽 다음으로.
- 같이 탈 수 없으면 → 가장 무거운 사람은 어차피 아무와도 못 타므로(가장 가벼운 사람과도 안 되면 다른 누구와도 안 됨) **혼자 보트에 태움**.

### 왜 이게 최적인가 (탐욕법 정당성)

가장 무거운 사람 `H`를 생각해보자. `H`는 결국 누군가와 짝을 짓거나 혼자 타야 한다. 만약 `H`가 짝을 지을 수 있다면, **그 짝으로 가장 가벼운 사람 `L`을 선택하는 게 항상 손해가 없다** — 왜냐하면 `L`은 나머지 사람 중 누구와 짝을 지어도 성립하는(무게가 가장 작으므로) "가장 만만한" 사람이라, `H`가 아닌 다른 누군가와 `L`을 억지로 묶어두는 것보다 `H`와 묶어서 `H`를 먼저 처리해버리는 편이 이후 선택의 폭을 줄이지 않는다. 이 논리를 반복 적용하면 투 포인터 방식이 항상 최적해를 만든다는 게 증명된다.

### 손으로 시뮬레이션 — `people=[70,50,80,50], limit=100`

정렬하면 `[50, 50, 70, 80]`. `left=0`, `right=3`에서 시작.

| 단계 | left | right | people[left]+people[right] | 판정 | 처리 | boats |
|---|---|---|---|---|---|---|
| 1 | 0 (50) | 3 (80) | 130 | `>100` 같이 못 탐 | `right--` (무거운 사람 단독 탑승) | 1 |
| 2 | 0 (50) | 2 (70) | 120 | `>100` 같이 못 탐 | `right--` | 2 |
| 3 | 0 (50) | 1 (50) | 100 | `≤100` 같이 탐 | `left++`, `right--` | 3 |

`left(1) > right(0)`이 되어 종료. 총 **3대**. 예상과 일치.

## 3. 코드 (Java)

```java
import java.util.Arrays;

class Solution {
    public int solution(int[] people, int limit) {
        Arrays.sort(people);

        int left = 0;
        int right = people.length - 1;
        int boats = 0;

        while (left <= right) {
            if (left != right && people[left] + people[right] <= limit) {
                left++;   // 가장 가벼운 사람도 함께 태움
            }
            right--;      // 가장 무거운 사람은 항상 처리 완료 (같이 탔든 혼자 탔든)
            boats++;
        }

        return boats;
    }
}
```

### 코드 설명

- `left`는 아직 안 태운 사람 중 가장 가벼운 쪽, `right`는 가장 무거운 쪽을 가리킨다.
- **매 반복은 `right`가 가리키는 가장 무거운 사람 한 명을 반드시 처리**한다 — 같이 탈 짝이 있으면 `left`도 같이 전진시키고, 없으면 `right`만 전진(혼자 탑승).
- `left != right` 체크: 남은 사람이 한 명뿐일 때 자기 자신과 비교해서 이중으로 세는 걸 방지.
- 매 반복마다 `boats++` 이므로, 반복 횟수 자체가 곧 필요한 보트 수다.

## 4. 지금 작성 중인 코드와 비교 — 로직은 맞지만 속도가 다름

현재 작성 중인 버전도 **정렬 + 가장 가벼운/무거운 매칭**이라는 탐욕법 아이디어 자체는 정확히 같다.

```java
for (int i = 0; i < n; i++) {
    if (people[i] == 0) continue;
    answer++;
    for (int j = n - 1; j > i; j--) {          // ← 매번 오른쪽 끝부터 다시 스캔
        if (people[j] != 0 && people[i] + people[j] <= limit) {
            people[j] = 0;
            break;
        }
    }
    people[i] = 0;
}
```

차이는 **짝을 찾는 방식**이다. 투 포인터 버전은 `right` 포인터를 한 번 지나간 자리로 다시 돌아가지 않지만, 이 버전은 매 `i`마다 `j`를 `n-1`부터 다시 훑는다. 이미 앞서 처리된 사람들(`people[j]==0`으로 표시된 자리)까지 매번 다시 지나가야 해서, 최악의 경우(짝이 잘 안 맞아서 안쪽 루프가 끝까지 도는 경우) `O(n²)`이 된다.

1,000회 무작위 입력으로 두 버전이 **항상 같은 답**을 내는 것부터 확인했고, 이어서 최악 케이스(`n=50,000`, 전원 몸무게 200·제한 200이라 아무도 짝을 못 맺는 상황)로 실제 속도를 재봤다.

| 방식 | 시간복잡도 | n=50,000 최악 케이스 실측 |
|---|---|---|
| 투 포인터 | O(n log n) (정렬이 지배) | 약 0.3ms |
| 현재 작성 중인 방식 (중첩 스캔) | O(n²) | 약 568ms |

약 2,000배 차이가 나지만, 568ms도 프로그래머스의 일반적인 시간 제한(보통 1초 안팎) 안에는 들어온다 — 이 문제의 `n ≤ 50,000` 규모에서는 현재 방식도 통과할 가능성이 높다는 뜻이다. 다만 여유가 크지 않고, 입력이 조금만 더 컸다면 위험했을 구조이므로 투 포인터 방식으로 정리해두는 걸 권장한다.

## 5. 복잡도 분석 (투 포인터 기준)

- **시간복잡도**: `O(n log n)` — 정렬이 지배적. 투 포인터 자체는 `O(n)`.
- **공간복잡도**: `O(1)` 추가 공간 (정렬은 보통 in-place 또는 `O(log n)` 내부 스택).

## 6. 엣지 케이스

- 사람이 1명뿐인 경우: `left == right`라 조건문에서 짝을 짓지 않고 바로 혼자 탑승 → `boats = 1`.
- 모두 짝을 지을 수 있는 경우(가벼운 사람들로만 구성): `left`, `right`가 매 단계 서로를 향해 좁혀지며 `n/2`대(홀수면 `⌈n/2⌉`)로 수렴.
- 아무도 짝을 지을 수 없는 경우(모두 무거운 사람들): 매 단계 `right`만 줄어들어 `n`대가 필요.
