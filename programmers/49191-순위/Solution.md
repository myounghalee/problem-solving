# [프로그래머스 49191] 순위 — 승/패 관계의 전이적 폐포(transitive closure) 구하기

- 문제 번호: 49191
- 링크: https://school.programmers.co.kr/learn/courses/30/lessons/49191
- 분류: 그래프
- 사용 자료구조/알고리즘: **DFS로 승/패 관계 전파** (+ 대안: **플로이드–워셜**)

## 1. 문제 요약

n명의 선수가 참여한 토너먼트에서 일부 경기 결과(`results[i] = [A, B]`, A가 B를 이김)만 주어진다. 어떤 선수의 순위는, **그 선수와 나머지 (n-1)명 전원 사이의 승패 관계가 (직접 또는 간접적으로) 모두 확정될 때** 정해질 수 있다. 정확하게 순위를 매길 수 있는 선수의 수를 반환한다.

## 2. 접근 아이디어

핵심 관찰: A가 B를 이기고 B가 C를 이기면, **A는 C도 이긴 것으로 확정**된다(전이성). 이 문제는 결국 "이겼다/졌다"라는 두 가지 관계를 **그래프의 도달 가능성(reachability)** 문제로 바꿔서, 모든 쌍에 대해 전이적으로 관계를 닫아주는 문제다.

- `plays[i][j]`에 `'W'`(i가 j를 이김) / `'L'`(i가 j에게 짐) / 미정(`0`)을 저장한다.
- 직접 주어진 경기 결과로 `plays`를 초기화한 뒤, **전이적 관계를 전파**해서 간접적으로 알 수 있는 승패까지 채운다.
- 마지막에 각 선수 `i`에 대해 `plays[i][*]`에서 값이 채워진 칸의 개수를 세어, 그 개수가 `n - 1`(자기 자신 제외 전원)이면 순위가 확정된 것으로 카운트한다.

전이적 관계를 채우는 방법은 여러 가지가 있는데, 이 풀이는 **DFS로 각 시작점에서 관계를 퍼뜨리는 방식**을 쓴다. 아래 5절에서는 **플로이드–워셜**로 같은 문제를 푸는 대안도 함께 다룬다.

### 손으로 시뮬레이션 — `n = 5`, `results = [[4,3],[4,2],[3,2],[1,2],[2,5]]`

직접 주어진 관계로 `plays`를 초기화하면 (1-인덱스로 표기, `W`=이김, `L`=짐, `.`=미정):

|   | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| 1 | . | W | . | . | . |
| 2 | L | . | L | L | W |
| 3 | . | W | . | L | . |
| 4 | . | W | W | . | . |
| 5 | . | L | . | . | . |

`2번` 행이 이미 4칸(1, 3, 4, 5) 전부 채워져 있다 — 직접 경기 결과만으로도 `2번`은 순위가 확정된다.

이제 전파를 해보자. 예를 들어 `1번은 2번을 이겼고(W)`, `2번은 5번을 이겼으므로(W)`, 전이적으로 **`1번도 5번을 이긴 것`**으로 확정된다(`1 → 2 → 5`). 같은 방식으로 `3번(3→2→5)`, `4번(4→2→5)`도 각각 `5번`을 이긴 것으로 확정된다. 즉 **`2번`에게 진 선수(1, 3, 4)는 전부 `2번`을 이긴 적이 있는 다른 선수에게도 지는 게 아니라, `2번`이 이긴 `5번`을 자신들도 이긴 것으로 확정**되는 것이다. 전파를 마치면:

|   | 1 | 2 | 3 | 4 | 5 | 확정된 상대 수 |
|---|---|---|---|---|---|---|
| 1 | . | W | . | . | **W** | 2 |
| 2 | L | . | L | L | W | **4 → 확정** |
| 3 | . | W | . | L | **W** | 3 |
| 4 | . | W | W | . | **W** | 3 |
| 5 | **L** | L | **L** | **L** | . | **4 → 확정** |

`5번`은 `1, 3, 4` 모두에게 새로 `L`이 채워지면서(자신을 이긴 `2번`을 이긴 선수들에게는 자신도 졌을 수밖에 없으므로) 4칸이 전부 채워져 순위가 확정된다. 반면 `1번`, `3번`, `4번`은 서로 간의 직접 대결 기록이 없어 여전히 몇몇 칸이 미정으로 남는다.

**결과: 확정된 상대 수가 `n-1(=4)`인 선수는 `2번`, `5번` 두 명 → 정답 `2`.**

## 3. 코드 (Java) — DFS로 관계 전파

```java
class Solution {

    char[][] plays;

    public int solution(int n, int[][] results) {
        plays = new char[n][n]; // plays[i][j]: i가 j에게 'W'(승) / 'L'(패), 미정이면 0

        for (int[] result : results) {
            plays[result[0] - 1][result[1] - 1] = 'W';
            plays[result[1] - 1][result[0] - 1] = 'L';
        }

        for (int i = 0; i < n; i++) {
            for (int j = 0; j < n; j++) {
                if (i == j) continue;
                if (plays[i][j] == 'W' || plays[i][j] == 'L') {
                    dfs(i, j, n); // i-j 관계를 j를 거쳐 다른 선수에게 전파
                }
            }
        }

        int answer = 0;
        for (char[] row : plays) {
            int sum = 0;
            for (char col : row) {
                sum += col == 0 ? 0 : 1; // 관계가 확정된 상대 수
            }
            if (sum == n - 1) answer++; // 나머지 전원과의 관계가 확정되면 순위 확정
        }

        return answer;
    }

    private void dfs(int i, int j, int n) {
        char temp = plays[i][j]; // i -> j 관계 (W 또는 L)
        char temp2 = temp == 'W' ? 'L' : 'W'; // 반대편(j -> i, k -> i)에 채울 관계
        for (int k = 0; k < n; k++) {
            if (k == i) continue;
            if (plays[j][k] == temp && plays[i][k] != temp) { // 아직 i-k가 같은 관계로 확정되지 않았을 때만 전파
                plays[i][k] = temp;
                plays[k][i] = temp2;
                dfs(i, k, n);
            }
        }
    }
}
```

### 코드 설명

- `dfs(i, j, n)`은 "`i`가 `j`와 이미 `temp`(W 또는 L) 관계"라는 사실을 바탕으로, `j`가 갖고 있는 같은 관계(`plays[j][k] == temp`)를 `i`에게도 그대로 옮겨 적는다(`i`가 `j`를 이겼고 `j`가 `k`를 이겼으면, `i`도 `k`를 이긴 것). 옮겨 적은 뒤에는 그 `k`를 새로운 경유지 삼아 `dfs(i, k, n)`으로 계속 파고든다.
- **`plays[i][k] != temp` 체크가 핵심이다.** 이게 없으면 이미 확정된 관계를 향해서도 무한정 재귀를 반복하게 되는데, 촘촘한 그래프(경기 결과가 많은 경우)에서는 `i`에서 `k`까지 도달하는 경유 경로가 여러 개 존재해서 같은 갱신을 기하급수적으로 중복 수행하게 된다. 이 체크로 각 `(i, k)` 쌍은 최대 한 번만 확정·재귀되도록 막아준다.
- `plays[k][i] = temp2`로 반대 방향도 같이 채워서, 나중에 `k`를 기준으로 순회할 때도 별도 전파 없이 바로 `i`와의 관계를 알 수 있게 한다.

## 4. 복잡도 분석

- **시간복잡도**: `O(n²)` — 방문 체크(`plays[i][k] != temp`) 덕분에 각 `(i, k)` 쌍은 최대 한 번만 갱신·재귀되므로, `dfs` 호출 전체 횟수가 `O(n²)`으로 제한된다. `n <= 100`이므로 여유롭게 통과한다.
- **공간복잡도**: `O(n²)` — `plays` 배열, 재귀 깊이는 최악의 경우 `O(n)`.

> **주의**: 방문 체크(`plays[i][k] != temp`)가 없는 버전은 촘촘한 그래프에서 `dfs` 호출이 기하급수적으로 늘어나 시간초과가 난다. `n=100`에 4500개(거의 완전 토너먼트)의 경기 결과를 넣고 테스트해보면, 체크가 없는 버전은 20초가 지나도 끝나지 않는 반면 체크를 추가한 버전은 1ms 안에 끝난다.

## 5. 대안: 플로이드–워셜로 풀기 — O(n³)

DFS 대신, **경유지(k)를 최외곽 루프로 둔 삼중 루프**(표준 플로이드–워셜 형태)로도 같은 전이적 폐포를 구할 수 있다. `n <= 100`이라 `O(n³) = 10^6`으로 충분히 빠르다.

```java
class Solution {
    public int solution(int n, int[][] results) {
        boolean[][] beats = new boolean[n][n]; // beats[i][j] = i가 j를 이긴다(직접/간접 모두 포함)

        for (int[] r : results) {
            beats[r[0] - 1][r[1] - 1] = true;
        }

        for (int k = 0; k < n; k++) {          // 경유지가 반드시 최외곽 루프여야 한 번의 삼중 루프로 정확한 결과가 나온다
            for (int i = 0; i < n; i++) {
                if (!beats[i][k]) continue;
                for (int j = 0; j < n; j++) {
                    if (beats[k][j]) beats[i][j] = true; // i가 k를 이기고 k가 j를 이기면, i도 j를 이긴 것
                }
            }
        }

        int answer = 0;
        for (int i = 0; i < n; i++) {
            int known = 0;
            for (int j = 0; j < n; j++) {
                if (i == j) continue;
                if (beats[i][j] || beats[j][i]) known++; // i가 이겼거나, i가 졌거나(=상대가 i를 이김)
            }
            if (known == n - 1) answer++;
        }

        return answer;
    }
}
```

**왜 `k`가 최외곽이어야 하는가?** 플로이드–워셜이 한 번의 삼중 루프만으로 정확한 전이적 폐포를 구하려면, `beats[i][k]`와 `beats[k][j]`를 참조하는 시점에 그 값들이 **"0..k-1까지의 모든 경유지를 이미 고려해서 확정된" 상태**여야 한다. `k`가 최외곽이면 이 조건이 자동으로 보장된다. 만약 경유지 역할을 하는 변수가 최외곽이 아니라 더 안쪽 루프에 있으면(예: DFS 버전의 원래 시도처럼 `i`가 최외곽이고 경유지가 중간 루프), 경유지들을 훑는 순서가 실제 연쇄 순서와 어긋날 때 일부 전이 관계를 놓칠 수 있다.

| | DFS 전파 | 플로이드–워셜 |
|---|---|---|
| 시간복잡도 | `O(n²)` (방문 체크 시) | `O(n³)` |
| 구현 형태 | 재귀, 경유지 체크 필요 | 삼중 루프, 순서(k 최외곽)만 지키면 항상 정확 |
| 실수하기 쉬운 지점 | 방문 체크 누락 → 지수적 시간초과 | 경유지 루프 순서 오류 → 일부 관계 누락(오답) |

두 방식 모두 이 문제의 제약(`n <= 100`) 안에서는 충분히 빠르지만, 플로이드–워셜 쪽이 순서만 지키면 항상 정확하다는 점에서 구현 실수 여지가 더 적다.

## 6. 엣지 케이스

- **경기 결과가 모순 없이 주어진다는 가정**: `plays[i][j]`와 `plays[j][i]`가 동시에 다른 값으로 세팅될 일은 없다(문제 제약).
- **경기 결과가 매우 적은 경우**(`results.length = 1`): 대부분의 선수가 나머지와 관계가 확정되지 않아 순위가 매겨지는 선수 수가 적다(직접 경기를 치른 2명조차, 그 둘을 제외한 다른 선수들과의 관계가 없으면 확정되지 않는다).
- **거의 완전한 토너먼트**(`results.length`가 최대치 `4500`에 가까운 경우): 대부분(또는 전부)의 관계가 전이적으로 확정되어 답이 `n`에 가까워진다. 이 케이스가 바로 DFS 버전에서 방문 체크가 없으면 시간초과가 나는 경우다.
