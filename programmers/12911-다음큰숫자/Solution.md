# [프로그래머스 12911] 다음 큰 숫자 — 브루트포스로 충분한 이유, 그리고 O(1) 비트 트릭

- 문제 번호: 12911
- 링크: https://school.programmers.co.kr/learn/courses/30/lessons/12911
- 분류: 연습문제
- 사용 자료구조/알고리즘: **브루트포스(정답) + 비트 조작(참고용 최적화)**
- 난이도 체감: Lv.1 (브루트포스로 바로 통과되지만, 왜 통과되는지 이해하고 넘어가면 좋음)

## 1. 문제 요약

자연수 `n`이 주어질 때, 다음 세 조건을 만족하는 **가장 작은** 수를 구한다.

1. `n`보다 크다.
2. 2진수로 변환했을 때 `1`의 개수가 `n`과 같다.

```text
78 (1001110, 1이 4개) → 83 (1010011, 1이 4개)
15 (1111, 1이 4개)    → 23 (10111, 1이 4개)
```

**제한사항**: `n`은 1,000,000 이하의 자연수.

## 2. 접근 아이디어 — 브루트포스로 충분하다

가장 직관적인 방법은 `n+1`부터 하나씩 올려가며, 2진수 `1`의 개수가 원래 `n`과 같아지는 첫 수를 찾는 것이다.

```text
n=78 (1이 4개)
79(1001111,1이5개) 아님 → 80(1010000,1이2개) 아님 → 81(1010001,1이3개) 아님
→ 82(1010010,1이3개) 아님 → 83(1010011,1이4개) 일치! → 83 반환
```

문제만 보면 "이렇게 하나씩 다 세봐도 시간 안에 끝날까?"가 걱정될 수 있는데, 실제로 **끝까지 검증해보면 충분히 빠르다.**

## 3. 코드 (Java)

```java
class Solution {
    public int solution(int n) {
        int targetCount = Integer.toBinaryString(n).replace("0", "").length();
        int currentCount = 0;

        while (targetCount != currentCount) {
            n++;
            currentCount = Integer.toBinaryString(n).replace("0", "").length();
        }

        return n;
    }
}
```

### 코드 설명

- `Integer.toBinaryString(n)`으로 `n`을 이진수 문자열로 바꾸고(`"1001110"`), `.replace("0", "")`로 `0`을 전부 지워서 `1`만 남긴 뒤 `.length()`로 개수를 센다 — `n`의 popcount(1비트 개수)를 구하는 방법이다.
- 그 popcount와 같아질 때까지 `n`을 1씩 늘려가며 매번 다시 센다.

## 4. 왜 브루트포스가 시간 안에 끝나는가 — 실측

"1씩 다 세본다"는 방식이 걱정되는 지점은 **최악의 경우 몇 번이나 반복하는가**다. 직접 `n = 1`부터 `1,000,000`까지 전수 조사해서 반복 횟수가 가장 큰 지점을 찾아봤다.

```text
1~1,000,000 전수조사 결과 최대 반복 = 524,288회 (n = 524,288 일 때)
```

`n = 524288 = 2¹⁹` (이진수로 `1` 다음에 `0`이 19개, popcount = 1)일 때가 최악이다. popcount가 1인 다음 수는 `2²⁰ = 1,048,576`이므로, 그 사이 524,288개의 수를 전부 건너뛰어야 한다 — **2의 거듭제곱이 항상 최악의 케이스**다 (popcount가 1인 수는 2의 거듭제곱뿐이고, 그다음 popcount 1인 수는 정확히 두 배 떨어져 있기 때문).

이 최악의 케이스 하나만 따로 시간을 재보면:

```text
solution(524288) = 1048576, 약 57ms
```

프로그래머스 채점 시간 제한(보통 1초 안팎)에 비하면 충분히 여유롭다. 즉 **이 문제의 실제 입력 범위(`n ≤ 1,000,000`)에서는 브루트포스가 정답이자 충분히 효율적인 풀이**다. [멀리 뛰기(12914)](../12914-멀리뛰기/Solution.md)의 지수 시간 재귀처럼 "느려서 진짜 시간 초과가 나는" 경우와는 다르다 — 여기서는 걱정과 달리 브루트포스 자체가 통과선 안에 들어온다.

### 참고: `Integer.bitCount()`를 썼다면 더 빨랐을까

`Integer.toBinaryString(n).replace("0", "")`는 호출마다 문자열을 새로 만드는 반면, `Integer.bitCount(n)`은 문자열 생성 없이 비트 연산만으로 popcount를 구하는 JVM intrinsic이라 훨씬 가볍다. `n=1`부터 `1,000,000`까지 전부 호출해서 비교하면:

| 방식 | 1~1,000,000 전체 호출 시간 |
|---|---|
| `Integer.toBinaryString(n).replace("0","")` | 약 1,494ms |
| `Integer.bitCount(n)` | 약 30ms |

약 50배 차이가 난다. 다만 실제 채점은 **한 번의 `n`에 대해 한 번만 호출**되므로, 최악의 단일 호출 기준(57ms)으로는 두 방식 다 문제없이 통과한다. 그래도 습관적으로는 `Integer.bitCount(n)`을 쓰는 게 더 낫다.

## 5. 더 빠른 방법 — O(1) 비트 트릭 (참고용)

브루트포스로도 이 문제는 충분하지만, "같은 개수의 1비트를 가지는 다음으로 큰 수"를 구하는 건 잘 알려진 비트 트릭이 있다 — 반복 없이 상수 번의 비트 연산만으로 끝난다.

```java
class Solution {
    public int solution(int n) {
        int lowestBit = n & -n;                    // 최하위 1비트만 남김
        int rippled = n + lowestBit;                // 그 1비트를 한 자리 위로 올림(캐리 전파)
        int ones = ((rippled ^ n) >> 2) / lowestBit; // 캐리 과정에서 사라진 1들을 오른쪽 끝에 채워 넣을 값
        return ones | rippled;
    }
}
```

**동작 원리 (n=78, `1001110`)**:
1. `lowestBit = n & -n` → 최하위 1비트만 추출 (`0000010` = 2)
2. `rippled = n + lowestBit` → 최하위 1비트를 그 다음 자리로 밀어 올림 (`1010000` = 80). 이 과정에서 그 아래에 있던 `1`들은 캐리에 흡수되어 전부 `0`이 된다.
3. `rippled ^ n` → 바뀐 비트 구간만 추출 (`0011110`), `>> 2`로 정렬해서 "사라진 1의 개수 - 2"만큼의 `1`이 오른쪽에 뭉쳐 있는 값을 만든다.
4. 그 값을 `lowestBit`으로 나누면, 사라진 `1`의 개수만큼을 최하위 비트들로 옮겨 담은 값이 나온다.
5. `rippled`와 OR 하면, "한 자리 올린 결과" + "사라진 1들을 맨 오른쪽에 다시 채운 결과" = 다음 큰 수.

브루트포스 결과와 `1`부터 `1,000,000`까지 **전수 비교해서 전부 일치함을 확인**했고, 최악의 케이스(`n=524288`)도 `0.0002ms` 수준으로 끝난다 — 반복문 자체가 없어서 `n`의 크기와 무관하게 항상 일정한 시간이 걸린다.

## 6. 복잡도 분석

| 방식 | 시간복잡도 | 이 문제(`n≤1,000,000`)에서 실측 |
|---|---|---|
| 브루트포스 (문자열 popcount) | 최악 O(gap) — gap은 다음 같은 popcount까지의 거리, 최악 524,288 | 최악 57ms |
| 브루트포스 (`Integer.bitCount`) | 위와 동일, 상수 인자만 작음 | 전체 스윕 30ms |
| 비트 트릭 | O(1) | 사실상 0ms |

## 7. 엣지 케이스

- **2의 거듭제곱** (`1`, `2`, `4`, ..., `524288`): popcount가 1이라 다음 popcount-1 수도 그다음 2의 거듭제곱뿐 — 브루트포스 최악 케이스.
- `n = 1,000,000` (최댓값 근처): 브루트포스로도 충분히 빠르게 처리됨 (별도 실측 불필요할 만큼 여유).
