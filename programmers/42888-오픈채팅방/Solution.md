# [프로그래머스 42888] 오픈채팅방 — 해시맵으로 최종 닉네임만 따로 관리하기

- 문제 번호: 42888
- 링크: https://school.programmers.co.kr/learn/courses/30/lessons/42888
- 분류: 2019 KAKAO BLIND RECRUITMENT
- 사용 자료구조/알고리즘: **해시맵(HashMap)**
- 난이도: Lv.2

## 1. 문제 요약

채팅방 입장/퇴장/닉네임 변경 기록(`record`)이 순서대로 주어진다. **모든 기록이 처리된 뒤**, 방장이 보게 되는 최종 메시지 목록을 구한다.

핵심 규칙: 닉네임을 나중에 바꾸면, **과거에 이미 출력됐던 입장/퇴장 메시지의 닉네임도 전부 최신 닉네임으로 바뀐다.** 즉, 로그를 그대로 출력하면 안 되고, 각 유저의 **최종(가장 마지막) 닉네임**을 알아낸 뒤 그걸로 모든 입장/퇴장 메시지를 다시 채워야 한다.

```text
예시) record = ["Enter uid1234 Muzi", "Enter uid4567 Prodo", "Leave uid1234",
                "Enter uid1234 Prodo", "Change uid4567 Ryan"]
→ ["Prodo님이 들어왔습니다.", "Ryan님이 들어왔습니다.",
   "Prodo님이 나갔습니다.", "Prodo님이 들어왔습니다."]
```

첫 번째 `Enter uid1234 Muzi`도 uid1234의 최종 닉네임이 `Prodo`이기 때문에 `"Prodo님이 들어왔습니다."`로 출력된다.

**제한사항**
- `record` 길이: 1 ~ 100,000
- 각 줄은 `"Enter 유저ID 닉네임"`, `"Leave 유저ID"`, `"Change 유저ID 닉네임"` 중 하나
- 유저ID·닉네임은 영문 대소문자/숫자, 길이 1~10

## 2. 접근 아이디어

두 번 훑으면 된다.

1. **1차 순회 — 최종 닉네임만 기록**: `record`를 처음부터 끝까지 순회하며, `Enter`/`Change`가 나올 때마다 `유저ID → 닉네임` 해시맵을 계속 덮어쓴다. `Leave`는 닉네임 정보가 없으니 무시한다. 순회가 끝나면 해시맵에는 각 유저의 **가장 마지막 닉네임**만 남는다.
2. **2차 순회 — 메시지 재구성**: 다시 `record`를 처음부터 순회하되, 이번엔 `Enter`/`Leave`만 골라서 메시지를 만든다. 이때 기록에 적혀있던 닉네임이 아니라, **1차 순회에서 만든 해시맵에서 그 유저ID의 최종 닉네임을 찾아서** 사용한다. `Change`는 메시지를 직접 만들지 않으므로 건너뛴다.

이렇게 하면 "닉네임을 나중에 바꿔도 과거 메시지까지 소급 적용된다"는 문제의 핵심 조건이 자연스럽게 만족된다.

### 손으로 시뮬레이션 — 주어진 예시

**1차 순회 (해시맵 구성)**

| 처리한 줄 | 해시맵 상태 |
|---|---|
| `Enter uid1234 Muzi` | `{uid1234: Muzi}` |
| `Enter uid4567 Prodo` | `{uid1234: Muzi, uid4567: Prodo}` |
| `Leave uid1234` | 변화 없음 (Leave는 무시) |
| `Enter uid1234 Prodo` | `{uid1234: Prodo, uid4567: Prodo}` (덮어씀) |
| `Change uid4567 Ryan` | `{uid1234: Prodo, uid4567: Ryan}` (덮어씀) |

**2차 순회 (메시지 생성, `Enter`/`Leave`만)**

| 처리한 줄 | 유저ID로 찾은 최종 닉네임 | 생성된 메시지 |
|---|---|---|
| `Enter uid1234 Muzi` | `Prodo` | `Prodo님이 들어왔습니다.` |
| `Enter uid4567 Prodo` | `Ryan` | `Ryan님이 들어왔습니다.` |
| `Leave uid1234` | `Prodo` | `Prodo님이 나갔습니다.` |
| `Enter uid1234 Prodo` | `Prodo` | `Prodo님이 들어왔습니다.` |

정확히 기대 출력과 일치한다.

## 3. 코드 (Java)

```java
import java.util.*;

class Solution {
    public String[] solution(String[] record) {
        Map<String, String> user = new HashMap<>(); // 유저ID -> 최종 닉네임

        // 1차 순회: Enter/Change만 반영해서 각 유저의 마지막 닉네임을 계속 덮어씀
        for (String r : record) {
            String[] s = r.split(" ");
            if (!s[0].equals("Leave")) {
                user.put(s[1], s[2]);
            }
        }

        // 2차 순회: Enter/Leave만 골라, 해시맵에서 최종 닉네임을 찾아 메시지 생성
        StringBuilder sb = new StringBuilder();
        for (String r : record) {
            String[] s = r.split(" ");
            if (s[0].equals("Enter")) {
                sb.append(user.get(s[1])).append("님이 들어왔습니다.!");
            } else if (s[0].equals("Leave")) {
                sb.append(user.get(s[1])).append("님이 나갔습니다.!");
            }
        }
        return sb.toString().split("!"); // 구분자로 이어붙였다가 한 번에 배열로 쪼갬
    }
}
```

### 코드 설명

- `user` 맵은 "유저ID → 최종 닉네임"만 저장한다. `Change`뿐 아니라 `Enter`도 닉네임 정보를 갖고 있으므로(입장할 때도 닉네임을 정하니까), `!s[0].equals("Leave")`로 두 경우를 한 번에 처리한다.
- `record`를 두 번 순회하는 이유는, "최종 닉네임"이 그 유저의 **모든 기록을 다 봐야만** 확정되기 때문이다. 첫 번째 순회에서 전체를 훑어 최종 상태를 만들고, 두 번째 순회에서 그 확정된 정보를 참조해야 순서에 상관없이 정확한 메시지를 만들 수 있다.
- 메시지들을 배열에 바로 담는 대신 `StringBuilder`에 `!`를 구분자로 이어붙인 뒤 마지막에 `split("!")`로 한 번에 배열을 만든다. 닉네임 제약상(`영문 대소문자, 숫자만 가능`) 실제 메시지 안에는 `!`가 들어갈 수 없으므로 구분자로 안전하게 쓸 수 있다. `String.split`은 기본적으로 끝에 남는 빈 문자열을 제거해주므로, 마지막 `!` 뒤에 빈 문자열이 남는 것도 걱정할 필요가 없다.

## 4. 복잡도 분석

- **시간복잡도**: `O(n)` — `record`를 두 번(상수 배) 순회하며, 각 줄마다 `split`과 해시맵 연산이 상수/평균 `O(1)`(문자열 길이가 최대 10으로 고정되어 있어 사실상 상수). 전체적으로 `record` 길이 `n`에 선형.
- **공간복잡도**: `O(u)` — `u`는 서로 다른 유저 수(최대 `record` 길이만큼). 결과 배열도 `O(n)`.

`record` 길이가 최대 100,000이라는 제한에서 `O(n)`이면 충분히 빠르다.

## 5. 엣지 케이스

- **닉네임을 여러 번 바꾸는 경우**: 1차 순회가 매번 덮어쓰기 때문에, 몇 번을 바꾸든 마지막 값만 자연스럽게 남는다.
- **같은 유저가 나갔다가 다른 닉네임으로 다시 들어오는 경우**: `Leave`는 닉네임 갱신에 관여하지 않고, 그다음 `Enter`가 다시 최종 닉네임을 덮어쓰므로 순서대로 잘 처리된다.
- **여러 유저가 동시에 같은 닉네임을 쓰는 경우(중복 닉네임 허용)**: 메시지 생성은 유저ID 기준으로 이루어지므로, 닉네임이 같아도 유저ID가 다르면 서로 독립적으로 정확히 처리된다.
