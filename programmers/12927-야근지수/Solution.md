# [프로그래머스 12927] 야근 지수 — 탐욕법 + 최대 힙

- 문제 번호: 12927
- 링크: https://school.programmers.co.kr/learn/courses/30/lessons/12927
- 분류: 연습문제
- 사용 자료구조/알고리즘: **탐욕법(Greedy) + 최대 힙(PriorityQueue)**
- 난이도 체감: Lv.3 (왜 "가장 큰 걸 깎는 게 최적인지" 증명하는 부분이 핵심)

## 1. 문제 요약

작업량 배열 `works`가 있고, `N`시간 동안 매 시간 원하는 작업 하나를 골라 1씩 줄일 수 있다. `N`시간이 지난 뒤 **남은 작업량들의 제곱의 합(야근 피로도)**을 최소화해야 한다.

```text
works=[4,3,3], n=4 → 4시간 동안 깎아서 [2,2,2] → 2²+2²+2²=12
works=[1,1], n=3   → 총 작업량(2) ≤ n(3) → 전부 처리 → 0
```

**제한사항**: `works` 길이 1~20,000, 원소 최대 50,000, `n ≤ 1,000,000.`

## 2. 접근 아이디어 — 왜 "가장 큰 것부터 깎는 게" 항상 최적인가

직관적으로 "어차피 다 못 줄인다면, 값들을 최대한 고르게 만들어야 제곱합이 작아진다"는 걸 알 수 있다. 이걸 조금 더 엄밀하게 보면:

`x ≥ y`인 두 작업량이 있을 때, `x`를 1 줄이는 것과 `y`를 1 줄이는 것을 비교하면:

- `x`를 줄이면 제곱합 변화량: `(x-1)² - x² = -2x + 1`
- `y`를 줄이면 제곱합 변화량: `(y-1)² - y² = -2y + 1`

`x ≥ y`이므로 `-2x+1 ≤ -2y+1` — 즉 **더 큰 값을 줄일 때 제곱합이 더 많이(또는 같게) 줄어든다.** 그러므로 매 시간 항상 "현재 가장 큰 작업량"을 깎는 게 손해가 없다. 이 논리를 n번 반복 적용하면, 탐욕법이 전역 최적해를 만든다는 게 증명된다 (제곱 함수의 볼록성에서 나오는 전형적인 결과).

### 그래서 필요한 것: 매번 "현재 최댓값"을 빠르게 찾고 갱신하는 자료구조 → 최대 힙

배열을 매번 정렬해서 최댓값을 찾으면 한 번에 `O(k log k)`(k=works.length)가 들지만, **최대 힙**을 쓰면 최댓값 조회+갱신이 `O(log k)`로 끝난다. `n`번 반복하므로 전체는 `O(n log k)`.

### 손으로 시뮬레이션 — `works=[4,3,3], n=4`

최대 힙 `[4,3,3]`에서 시작.

| 시간 | 힙에서 꺼낸 최댓값 | 1 줄인 값 | 힙 상태 |
|---|---|---|---|
| 1 | 4 | 3 | [3,3,3] |
| 2 | 3 | 2 | [2,3,3] |
| 3 | 3 | 2 | [2,2,3] |
| 4 | 3 | 2 | [2,2,2] |

최종 `[2,2,2]` → `4+4+4=12`. 예상과 일치.

## 3. 코드 (Java)

```java
import java.util.Collections;
import java.util.PriorityQueue;

class Solution {
    public long solution(int n, int[] works) {
        long total = 0;
        for (int w : works) total += w;

        // 총 작업량이 n 이하면 전부 처리 가능 → 곧바로 0
        int loops = (int) Math.min(n, total);

        PriorityQueue<Integer> heap = new PriorityQueue<>(Collections.reverseOrder());
        for (int w : works) heap.add(w);

        for (int i = 0; i < loops; i++) {
            int max = heap.poll();
            heap.add(max - 1);
        }

        long answer = 0;
        for (int w : heap) {
            answer += (long) w * w;
        }
        return answer;
    }
}
```

### 코드 설명

- `PriorityQueue<>(Collections.reverseOrder())`: Java의 `PriorityQueue`는 기본이 **최소 힙**이라, `reverseOrder()`로 비교 순서를 뒤집어 **최대 힙**으로 사용한다.
- `loops = min(n, total)`: 총 작업량(`total`)이 이미 `n` 이하라면, `n`번을 다 채울 필요 없이 총 작업량만큼만 깎으면 나머지는 전부 0이 된다 (예#3). 이 최적화 없이 `n`번을 그대로 돌려도 정답은 같지만(0을 계속 깎아봤자 그대로 0), `n`이 `10⁶`까지 커질 수 있으므로 불필요한 반복을 미리 줄여둔다.
- 매 반복: 최댓값을 꺼내서(`poll`) 1 줄인 뒤 다시 넣는다(`add`). `PriorityQueue`의 `poll`/`add`는 각각 `O(log k)`.
- 마지막에 힙에 남은 모든 값의 제곱을 더해서 반환. 정답이 `int` 범위를 넘을 수 있어(`works` 최대 50,000일 때 `50,000² × 20,000`도 가능) `long`으로 누적한다.

## 4. 복잡도 분석

- **시간복잡도**: `O(n log k)` (`n ≤ 1,000,000`, `k = works.length ≤ 20,000`). `loops ≤ n`번 반복하고, 매번 힙 연산이 `O(log k) ≈ 15`.
- **공간복잡도**: `O(k)` — 힙 크기는 항상 `works.length`로 고정.

실측(`works.length = 20,000`, `n = 1,000,000`): **약 33ms**로 여유롭다.

## 5. 내가 작성한 코드와 비교 — 로직은 맞지만 "매번 전체 정렬"이 문제

현재 코드는 최댓값을 힙 대신 **매 시간마다 배열을 통째로 정렬**해서 찾는 방식이다.

```java
for (int i = 0; i < n; i++) {
    Arrays.sort(works);
    if (works[works.length - 1] > 0) works[works.length - 1]--;
}
```

"매 시간 가장 큰 값을 깎는다"는 탐욕법 아이디어 자체는 정확히 같다 — 500회 무작위 데이터로 두 버전이 **항상 같은 답**을 내는 것도 확인했다. 문제는 속도다. `Arrays.sort()` 한 번이 `O(k log k)`인데, 이걸 `n`번 반복하니 전체는 `O(n × k log k)`.

`works.length = 20,000`(최댓값)으로 고정하고 `n`을 늘려가며 실측한 결과:

| n | 실행 시간 |
|---|---|
| 2,000 | 68.8ms |
| 4,000 | 90.5ms |
| 8,000 | 161.3ms |

`n`에 거의 비례해서 늘어나는 게 보인다 (works.length가 고정이라 매 반복 비용이 일정하기 때문). 이 추세를 `n = 1,000,000`까지 그대로 연장하면 **대략 15~20초** 수준으로 추정된다 — 프로그래머스의 일반적인 시간 제한(1초 안팎)을 10배 이상 초과해서, 큰 입력에서는 **거의 확실하게 시간 초과**가 난다.

| 방식 | 시간복잡도 | 최대 스케일 실측/추정 |
|---|---|---|
| 최대 힙 | O(n log k) | 약 33ms (실측) |
| 매번 전체 정렬 | O(n × k log k) | 약 15~20초 (추정) |

## 6. 검증

두 버전을 500회 무작위 데이터(작은 규모)로 대조해서 **항상 같은 답**을 내는 것을 확인했다. 힙 버전은 공식 예시 3개도 전부 통과한다.

## 7. 엣지 케이스

- 총 작업량이 `n` 이하인 경우(예#3): 모든 작업이 0이 되어 피로도 0.
- `works.length == 1`: 힙 연산 없이도 사실상 단순 뺄셈과 같지만, 코드는 그대로 동작한다.
- `n = 0`: `loops = 0`이 되어 아무것도 깎지 않고 원본 그대로의 제곱합을 반환.
